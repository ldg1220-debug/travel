## 1. ★★ §3-b 작동 확인

**캐시 없는 지역**으로 확인했습니다.

```
포천 d2  (11,889ms — 라이브 생성)
   d1 첫 스팟 = 국립수목원   ★4.5
   d2 첫 스팟 = 고향나들이   ★4.2
```

**두 일자 모두 평점 있는 스팟이 1번입니다.** `preferRatedFirstStop` 정상입니다.
라우팅 이전에 적용하신 판단도 맞습니다 — 이후에 바꿨으면 구간 이동시간이 어긋났을 겁니다.

### 다만 기존 캐시는 옛 순서 그대로입니다

```
경주 d3 (캐시 적중)
   d1 첫 = 경주원조콩국                        ★없음
   d3 첫 = 경주 용황 광 옛날통닭 치킨 맥주 호프 저녁 야식  ★없음
```

**26시간 캐시가 만료돼야 반영됩니다.** 급하면 워밍 크론에서 강제 재생성하세요.

## 2. ★★★ §2 — 세션 판단이 맞았고 제가 틀렸습니다

> `"4회 반복이 동일"한 건 dedupeInFlight+26시간 캐시로도 설명되는 현상이지
>  "생성 로직이 일수 의존적"이라는 증거는 아니다`

캐시 없는 지역으로 다시 재봤습니다.

```
       d2 = 422 count:2 (321ms — 캐시)
```

**제가 본 d2 급감은 전부 캐시된 결과였습니다.**
오사카·교토·도쿄도 같은 이유일 가능성이 큽니다. 제 §2 결론을 철회합니다.

## 4. ★★★ 404 — 라우트가 실행되지 않습니다

NFC 정규화 배포 후 다시 쟀습니다.

```
경주/2박3일    404 · 501ms → 133ms
여수/2박3일    404 · 140ms → 122ms
포천/2박3일    404 · 147ms → 134ms
신베이/2박3일  404 · 131ms → 121ms
```

**전부 ~130ms 로 동일합니다.** 이전 1.2초보다도 빨라졌습니다.

```
경주·여수    ENABLED_COURSE_PAGES 에 있음     →  404 · 130ms
포천·신베이  목록에 없음 (404가 정상)         →  404 · 130ms
```

**목록에 있든 없든 응답이 구분되지 않습니다.**
라우트가 실행돼 화이트리스트에서 떨어진다면, 로그를 남기고 `notFound()` 를 부르는 경로와
아예 매칭 안 되는 경로가 **똑같이 130ms 일 수는 없습니다.**

```
130ms 는 정적 not-found 페이지 응답입니다.
page.tsx 가 실행되지 않고 있습니다.
```

## 9. 처리 결과 (이 세션이 추가)

### §1/§2 — 확인·철회 감사, 추가 조치 없음

`preferRatedFirstStop`(§1)과 `dedupeInFlight`(§2 관련)가 라이브 캐시 미스에서
실제로 잘 동작한다는 확인, 그리고 §2의 "구조적" 진단을 스스로 철회해준 것
모두 감사하다 — 별도 코드 변경은 필요 없었다. 기존 캐시가 옛 순서/옛 결과를
그대로 들고 있는 문제(§1 "다만 기존 캐시는...")는 26시간 TTL이 지나면
자연히 해소되므로, 강제 재생성 메커니즘은 이번 라운드에 추가하지
않았다 — 급하면 워밍 크론을 수동 실행(Vercel Cron Jobs 화면의 Run
버튼)하는 기존 수단으로 충분하다고 판단했다.

### §3 — 실패 응답 캐시 금지 (구현)

`courseBrief.ts`의 `buildBrief`가 스팟이 `MIN_VIABLE_SPOTS`(=3, `/api/
content/course-brief`의 `insufficient_spots` 기준과 같은 상수로 통일)
미만이면 구조 단계·최종 단계 두 캐시 쓰기 모두 건너뛰도록 고쳤다 —
`isCacheableBrief` 순수 함수로 뽑아 단위 테스트로 고정했다. 이제 실패
결과는 캐시되지 않으므로, 다음 요청이 처음부터 다시 시도할 기회를
갖는다(`dedupeInFlight`는 여전히 동시 요청만 하나로 합친다 — 순차적인
재시도까지 막지 않는다). 짧은 TTL로 캐시하는 방식(지시서가 제안한
대안)은 캐시 스키마에 항목별 TTL이 없어 더 큰 변경이 필요해, "아예
안 쓴다" 쪽을 택했다 — 지시서의 "이 기능이 필요하면"이라는 단서에
부합한다고 판단했다.

### §6 — ASCII 진단 라우트 추가 (구현)

`/course-test/gyeongju/3`을 그대로 만들었다 — `[region]`/`[days]`
슬러그를 내부 매핑 테이블로 실제 지역명("경주")·일수(3)로 바꾼 뒤,
실제 코스 페이지와 똑같이 `getCourseBrief`를 부른다. 함수 진입
직후 `[course-test]` 로그도 남긴다. **임시 진단용이라는 점을 코드
주석에 명시했다** — 원인이 확인되면 지워야 한다. 로컬 `next build`
에서는 `/course/[region]/[days]`와 마찬가지로 `ƒ`(동적)로 정상
등록됨을 확인했다.

### §5 (동근님 확인 사항)는 이 세션이 할 수 없다

Vercel Runtime/Build 로그 확인은 이 세션에 그 접근 권한이 없다 —
지시서가 이미 명시한 대로 사람의 확인이 필요한 부분이라 별도 코드
조치를 하지 않았다.

### §4 — 이번에도 근본 원인은 확정하지 못했다

`/course-test`가 배포 후 200을 준다면 한글 세그먼트 자체가 원인이라는
뜻이고, 그것도 404라면 `/course/[region]/[days]` 라우트(또는 그 파일이
의존하는 무언가)에 국한된 배포 문제라는 뜻이다 — 이 세션은 그 결과를
직접 관찰할 수 없어 다음 지시서를 기다린다.
