## 1. ★★★ 제가 틀렸습니다 — 결정성은 이미 확보돼 있습니다

앞 지시서 §5 에서 이렇게 썼습니다.

> `오늘 12:xx  경주 12곳 · 19.8km`
> `오늘 13:xx  경주  9곳 · 22.3km     ← 시간이 지나자 다른 결과`
> `구글이 재방문할 때마다 내용이 바뀝니다`

**days 를 섞어 비교한 제 실수였습니다.**

```
경주 days=1  →   6곳 · 29.1km
경주 days=2  →   9곳 · 22.3km     ← 제가 "달라졌다"고 본 값
경주 days=3  →  12곳 · 19.8km     ← 페이지가 실제로 쓰는 값
```

`/course/경주/2박3일` 은 **days=3** 을 씁니다. 제가 API 를 days=2 로 부르고 비교했습니다.

같은 days 로 두 번 불러봤습니다.

```
호출 1  12곳 · 19.8km · 경주원조콩국|테라로사 경주점|경주 황리단길|…
호출 2  12곳 · 19.8km · 경주원조콩국|테라로사 경주점|경주 황리단길|…
동일 ✅  (순서까지 완전히 같음)
```

**`dedupeInFlight` 로 충분합니다. temperature=0 이나 영구 캐시는 필요 없습니다.**
§5 를 철회합니다. 그 작업은 하지 마세요.

### 덤으로 — days 매핑도 맞습니다

9/22 첫 확인 때 본 `<title>` 이 이랬습니다.

```
"경주 2박3일 코스 — 12곳, 총 19.8km"
```

**days=3 의 값과 정확히 일치합니다.** "2박3일 → days=3" 매핑이 올바릅니다.

> AutoPipeline 쪽에서 `extractDays()` 가 "2박3일"·"3박4일"을 모두 days=2 로 보내던 버그를
> 찾아 고쳤는데, **트레쥴에는 같은 문제가 없습니다.**

## 3. ★★ 코스 첫 장소가 리뷰 0 입니다

```
경주 days=3  →  12곳 중 평점 없음 3곳

  1번  경주원조콩국                           ★없음 (리뷰 0)   ← 코스 시작점
       경주 용황 광 옛날통닭 치킨 맥주 호프 저녁 야식   ★없음 (리뷰 0)
       경주중앙시장                           ★없음 (리뷰 0)

**페이지가 열리면 방문자가 가장 먼저 보는 장소가 리뷰 0인 콩국집입니다.**

```

## 7. 처리 결과 (이 세션이 추가)

### §1 — 철회를 그대로 반영한다

`dedupeInFlight`(PR #263)를 되돌리거나 temperature=0/영구 캐시를 새로 넣는 작업은
**하지 않았다** — 지시서의 철회를 그대로 따른다. 같은 days로 반복 호출하면
스팟 구성·순서까지 완전히 동일하다는 실측(§1)은 이전 라운드의 `dedupeInFlight` +
라이브 폴백 복구 조합이 실제로 유효하다는 방증이라 특별히 반갑다.

### §2 — 이번 라운드엔 추가 조치가 없다

코드에서 더 좁힐 수 있는 지점을 다시 찾아봤다(디렉터리 이름의 바이트 단위
확인 — `[region]`/`[days]`가 순수 ASCII임을 재확인, `/course` 아래 중복
라우트 존재 여부 재확인 — 없음). 새로운 단서는 없었다. PR #264(전체
에러 캐치 + `runtime="nodejs"`)가 이미 배포돼 있으니, 이번 라운드는 §2에
코드를 더 얹지 않고 Cowork의 재확인을 기다린다 — 같은 "즉시 404" 증상이
그 배포 이후에도 그대로면, 예외 처리로는 못 잡는 진짜 배포/라우팅 인프라
문제라는 뜻이고, 그건 이 세션이 코드로 해결할 수 있는 범위 밖이다.

### §3 — "소"로 보이지만 실제로는 깊은 변경이 필요해 이번엔 보류했다

원인을 추적했다: 국내(카카오) 후보는 `generateCourseV2`가 실제로 스팟을
**선택하는 시점**엔 rating/reviewCount를 거의 항상 모른다(카카오 검색
API가 그 필드를 안 준다 — 기존 주석에도 있는 내용). 이 경우
`courseTaste.ts`의 `deterministicTaste`가 카카오 검색 순위 기반 폴백
점수(`Math.max(10 - searchRankIndex*1.2, 1)`, 1위면 10점)를 쓰는데, 이
폴백 점수는 **잘 평가된 곳의 점수(rating×log10(reviews+10), 예: 평점
4.5·리뷰 1000이면 약 13.5점)와 크게 차이 나지 않는다** — "검색 1위지만
리뷰 0곳"과 "평점 4점대 잘 알려진 곳"이 선택 단계에서 비슷한 무게로
경쟁한다는 뜻이다. course-brief에 최종적으로 찍히는 평점·리뷰수는 이
선택이 끝난 **뒤에** `catalogRatingFor`/`liveDomesticRatingFor`가 별도로
붙이는 것이라, "경주원조콩국"이 실제로 리뷰 0인 걸 시스템이 아는 시점은
이미 그 장소가 코스에 들어간 다음이다.

이 폴백 점수(`deterministicTaste`)는 `courseTaste.test.ts`에 명시적으로
고정된 동작이고, course-brief만이 아니라 인터랙티브 코스 만들기·리롤
전체가 공유하는 함수다 — 여기를 손대면 이 페이지만이 아니라 앱 전체의
추천 결과가 바뀐다. 이 세션은 실제 카카오/구글 데이터로 그 효과를
검증할 방법이 없다(DB·외부 API 접근 없음).

"코스 조립 이후(라우트 계산 뒤)에 평점 0인 스팟만 골라 빼는" 방식도
검토했지만, `buildBrief`의 구조상 구간 이동시간(`toNextMinutes`)이
스팟 제거 이전에 이미 계산돼 있어(라우팅이 평점 부여보다 먼저 일어난다)
스팟 하나를 사후에 빼면 그 앞 스팟의 "다음 이동" 정보가 존재하지 않는
스팟을 가리키게 된다 — 이것도 선택 로직이 아니라 조립 순서 자체를
바꿔야(평점 부여를 라우팅보다 먼저 하도록) 하는 구조 변경이다.

**두 경로 다 "소" 크기가 아니라, 공유 추천 로직이나 파이프라인 순서를
바꾸는 변경이고, 라이브 데이터로 검증할 방법이 없는 채로 진행하면
지시서 §3 자체가 인용한 AutoPipeline 사례(리뷰 7,771인 황리단길까지
잘려 경주 전체가 스킵된 사고)와 같은 종류의 회귀를 낼 위험이 있다고
판단해, 이번 라운드에는 구현하지 않았다.** 원인 추적 결과는 다음 라운드
(또는 실제 데이터로 검증 가능한 누군가)가 바로 쓸 수 있도록 여기 남긴다.

### §4 — 원인을 특정하지 못했다

`THEME_SLOTS`/`buildDynamicSlots`는 날짜 수와 무관하게 하루 단위로
슬롯을 정의한다 — 코드 읽기로는 "일수가 줄면 슬롯/후보 자체가 줄어드는"
직접적인 로직을 찾지 못했다. 유력한 후보 두 가지를 확인했지만 어느 쪽도
확정하지 못했다:

- 해외 라이브 경로 조회(`ROUTING_BUDGET_MS`, `enrichBudgetMs`)의 예산
  안에서 스팟이 탈락하는 게 호출마다 달라질 수 있어(§1에서 확인했듯
  같은 days 반복 호출은 안정적이었지만, 서로 다른 days 사이의 비교는
  이번에 검증되지 않았다), 오사카 days=2가 우연히 나쁜 결과를 낸 것일
  가능성.
- `dedupeCrossDay`가 날짜가 적을수록 상대적으로 후보 겹침의 영향을 더
  받을 가능성 — 다만 이것도 코드 추적만으로는 "2곳까지" 떨어지는 걸
  설명할 만큼 확정적이지 않았다.

이 세션엔 카카오/구글 라이브 API·DB 접근이 없어 실제로 재현해 어느
가설이 맞는지 좁히지 못했다. `오사카 days=2`를 반복 호출해 매번 2곳이
나오는지(구조적 문제), 아니면 가끔 더 많이 나오는지(예산/타이밍 문제)
확인해주면 다음 라운드가 정확히 어디를 고칠지 좁힐 수 있다.
