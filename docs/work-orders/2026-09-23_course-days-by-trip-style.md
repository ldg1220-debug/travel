## 1. 3일 상한은 알고리즘 한계가 아닙니다

```ts
// courseBrief.ts
export function parseDays(value: string | null): 1 | 2 | 3 | null {
  if (value === "1") return 1;
  if (value === "2") return 2;
  if (value === "3") return 3;
  return null;               // → route.ts 가 400 "days must be 1, 2, or 3"
}
```

**하드코딩된 검증입니다.** 9/06 에 2→3 으로 늘렸고, 해외 코스가 30초에서 504 가 나 `maxDuration` 을 60 으로 올린 이력이 주석에 있습니다.
일자 배분(`chunkByProximity` · `reallocateStopsByDay`)은 일수를 인자로 받는 일반 구조입니다.

## 2. ★★★ 여행 스타일이 둘입니다

```
도시형   오사카 · 도쿄 · 방콕 · 타이베이 · 경주 · 전주 …

휴양형   세부 · 보라카이 · 보홀 · 팔라완 · 코타키나발루 · 발리(우붓·스미냑·쿠타)

**휴양형에 도시형 규칙을 쓰면 두 가지가 틀어집니다.**

② "후보 풀을 일수만큼 늘려라" →  안 가도 될 관광지를 채워 넣게 됨
```

## 4. ★★★ 스타일별 규칙

| | 도시형 | 휴양형 |
|---|---|---|
| 최대 일수 | **5** (4박5일) | **7** (5박7일) |
| 하루 스팟 | 4~5곳 | **2~3곳** |
| 최소 스팟 (`MIN_VIABLE_SPOTS`) | 일수 × 4 | 일수 × 2 |
| 후보 구성 | 관광지 · 맛집 · 카페 | **액티비티(호핑·스노클링·다이빙·투어) · 해변 · 스파/마사지 · 선셋 · 야시장 · 맛집** |
| 하루 이동 | 제약 없음 | **숙소권 반경 안** 위주, 하루 한 번만 멀리 |
| 6일 이상 | 거부 (보통 다도시 여행) | 허용 |

### 휴양형 코스의 모양

```
1일차   도착 · 리조트 주변 · 저녁 맛집
2일차   호핑투어(오전~오후) · 선셋
3일차   리조트 휴식 · 스파 · 야시장
4일차   당일 투어 1건 (먼 곳은 이 날 하루만)
5일차   해변 · 카페
…
```

**"리조트 휴식" 같은 빈 시간을 결함으로 보지 마세요.** 그게 휴양지 일정입니다.
빈 반나절을 억지로 관광지로 채우면 오히려 현실과 멀어집니다.

### 숙소권을 기준점으로

```
세부   = 세부시티(관광)  vs  막탄(리조트)
발리   = 우붓(내륙)      vs  스미냑·쿠타(해변)
```

휴양형은 **하루의 출발·도착점이 숙소권**이어야 합니다. 지역 좌표 앵커를 그대로 쓰되,
하루 동선이 앵커에서 멀어지는 날을 하루로 제한하세요.

## 5. ★★ 응답 시간

```
캐시 미스 실측 (days=3)   세부 19.2초 · 코타키나발루 14.9초 · 우붓 16.5초
maxDuration 60초
```

**휴양형은 하루 스팟이 적어서 7일이어도 구간 수가 도시형 5일보다 적습니다.**

```
도시형 5일 × 5곳 = 25곳 · 20구간
휴양형 7일 × 3곳 = 21곳 · 14구간   ← 오히려 가벼움
```

그래도 먼저 재주세요. `ROUTING_BUDGET_MS`(15초)는 구간 수에 비례하게 바꾸세요.

## 9. 처리 결과 (이 세션이 추가)

### §7 항목 1 — 실측, 수행 못 함

지시서가 "먼저"로 못박은 실측(세부 d5·d7, 오사카 d5 캐시 미스 응답시간)을
이 세션은 배포된 프로덕션/Vercel 접근 권한이 없어 직접 수행할 수 없었다.
아래 모든 구현은 이 실측 없이 진행됐다 — **60초를 넘는지 여부를 Cowork가
배포 후 가장 먼저 확인해야 한다.** 넘으면 지시서 안내대로 상한을 한 단계
낮추는 후속 라운드가 필요하다.

### §1·§6-2 — `parseDays` 확장, 완료

`courseBrief.ts`의 `parseDays`가 이제 "1"~"7" 정수 문자열을 전부 받는다
(형식만 검사 — `/^[1-7]$/`). 스타일별 상한(도시형 5·휴양형 7)은 지역을
알아야 판단할 수 있어 별도 함수 `maxDaysForStyle(style)`로 분리했다.
`course-brief`·`course-map`·`course-open` 세 라우트 모두 지역을 먼저
별칭 해석(`styleForRegion`, 내부에서 `resolveRegionAlias` 호출)해 스타일을
구하고, 요청한 일수가 그 상한을 넘으면 조용히 깎지 않고 400과 함께
`{ style, maxDays }`를 응답에 실어 허용 범위를 명시한다(지시서 §6-2
"메시지에 허용 범위 명시").

### §3·§6-1 — `RESORT_REGIONS` + `style` 필드, 완료

지시서가 제시한 20개 지역 이름 그대로 `discoverData.ts`에 `RESORT_REGIONS`를
추가했다(전부 기존 `WORLD_CITIES`/국내 카탈로그에 실존함을 확인). `FlatRegion`에
`style: "resort" | "city"` 필드를 추가하고 `attachRegionMeta`가 채운다 —
국내(서귀포·중문·애월 포함)·해외 양쪽 `flatRegions()` 모두 적용된다.
별칭을 먼저 해석하고 나서 판정한다(`styleForRegion`) — "발리"는
`RESORT_REGIONS`에 없지만 정본 "우붓"은 있어, 별칭 해석 없이 판정하면
스타일이 틀어진다.

### §4 — 스타일별 규칙, 부분 완료

- **최소 스팟(`MIN_VIABLE_SPOTS` → `minViableSpots(style, days)`)**: 지시서
  표(city: days×4, resort: days×2, 공통 바닥 3)를 그대로 구현했다.
  **⚠️ city는 days=1부터 기존 고정값(3)보다 엄격해진다**(1일=4, 2일=8,
  3일=12) — 기존 3은 "도시형 하루 4~5곳"이라는 실제 목표치보다 낮게
  잡혀 있었을 뿐이고, 이 지시서가 기준 자체를 올리라고 명시했다. 이
  세션은 실제 지역별 스팟 수 분포를 라이브로 확인할 수 없어, 기존에
  통과하던 일부 city 2·3일 요청이 새로 `insufficient_spots`(422)를
  받게 될 가능성을 배제하지 못한다 — **Cowork가 배포 후 기존 city
  지역들의 응답을 광범위하게 재확인해야 한다.**
- **후보 구성**: `courseRecommend.ts`에 새 테마 `"resort"`를 추가했다
  (`THEME_SLOTS.resort`: 액티비티 투어·스파 마사지·야시장 맛집 3슬롯 —
  기존 테마들의 7슬롯 대신 지시서 "하루 2~3곳"에 맞춰 줄였다). 사용자가
  직접 고르는 값이 아니다 — `buildBrief`가 `styleForRegion(region)`이
  "resort"면 이 테마를, 아니면 기존 `DEFAULT_THEME`(balanced)을 자동으로
  쓴다. `CourseClient.tsx`(수동 코스 만들기)의 테마 선택 UI는 자체
  하드코딩 목록을 쓰므로 이 값이 추가돼도 그 화면엔 노출되지 않는다.
  **실제 후보(호핑·스노클링·스파 등)가 각 리조트 지역에서 잘 잡히는지는
  라이브 검증하지 못했다** — 키워드가 국내/해외 Places 검색에서 얼마나
  잘 맞는지 Cowork가 확인해야 한다.
- **숙소권 앵커 중심 하루 동선**: **이번 라운드에서는 구현하지 않았다.**
  기존 지리적 클러스터링(`reallocateStopsByDay`)이 어느 정도 하루 안의
  스팟을 가까이 묶어주긴 하지만, "하루 동선이 숙소권에서 멀어지는 날을
  하루로 제한"하는 명시적 제약은 없다. 이 제약은 `avoidCentroid`(현재
  "이전 날짜 중심에서 멀어지게" 하는 점수 페널티)와 정반대 방향의 새
  하드 제약(생성 자체를 한 앵커 반경 안으로 묶고, 예외적으로 하루만
  풀어주는 것)이 필요해 보이는데, 라이브 검증 없이 잘못 설계하면
  오히려 후보를 인위적으로 줄여 §2가 우려한 "세부 5박7일이 전부
  거부됨"을 재현할 위험이 있다고 판단해 보류했다. 다음 라운드에서
  실측을 바탕으로 다시 다뤄야 한다.

### §5 — 라우팅 예산 구간 수 비례, 완료

`ROUTING_BUDGET_MS`(기존 15000ms, 최대 3일·약 10구간 기준 실측값)는
그대로 두고, 실제 구간 수(전체 스팟 수 − 날짜 수)에 `ROUTING_BUDGET_MS_PER_SEGMENT`
(1500ms — 기존 값의 근사 단위 예산)를 곱한 값과 비교해 더 큰 쪽을 쓴다 —
기존 1~3일 실측 검증치 밑으로는 절대 줄지 않고, 구간이 늘어난
5·7일 요청에서만 예산이 늘어난다. 이 값이 실제로 충분한지는 §7 항목1과
마찬가지로 라이브 실측이 필요하다.

### §6-6 — 코스 페이지 라벨, 완료

`coursePages.ts`의 `daysToLabel`/`labelToDays`/`COURSE_PAGE_DAY_LABELS`를
1~7일 전부로 확장했다. days=6·7은 "6박7일"이 아니라 지시서 §6 원문
그대로 "5박6일"·"5박7일"이다(장거리 휴양지 상품의 흔한 표기 관례 —
계산으로 유도하지 않고 표를 그대로 옮겼다). `ENABLED_COURSE_PAGES`(실제
sitemap에 노출되는 목록)는 이번에 확장하지 않았다 — 라벨 체계가
갖춰졌을 뿐, 어떤 지역·일수 조합을 실제로 공개할지는 기존처럼 별도
단계적 판단이 필요하다.

### §6-7 — 워밍 크론, 변경 없음(확인만)

`warm-course-brief/route.ts`의 `WARM_TASKS`는 이번 라운드에서 건드리지
않았다 — 국내 1일·해외 2일·3일만 그대로 워밍하고, 4일 이상은 지시서
지시대로 요청 시(캐시 미스 라이브 생성)에만 만들어진다.
