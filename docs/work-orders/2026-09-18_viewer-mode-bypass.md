## 4. ★★★ 의심 지점

뷰어 모드 판정이 **URL이 아니라 휘발성 상태**에 걸려 있는 것 같습니다.

```
course-open  →  /planner/{shareToken} 로 리다이렉트
                 이때 viewerModeActive 를 state / sessionStorage 에 심음
                 ↓
          리마운트 · 토큰 갱신 · 탭 백그라운드 복귀 · 주기적 동기화
                 ↓
          viewerModeActive 가 초기값(false)으로 돌아감
                 ↓
          이후 autosave 가 "내 계획"으로 판단하고 저장
```

확인해주실 것:

```
1. viewerModeActive 가 어디에 저장되는가 (useState? ref? sessionStorage?)
2. 그 값을 읽기 전에 저장이 먼저 나가는 경로가 있는가 (mount 직후 sync)
3. 주기적 autosave / visibilitychange / focus 핸들러가 플래그를 다시 읽는가
4. 저장 대상 id 를 어디서 가져오는가 — "마지막으로 본 내 계획" 이면 그게 원인
```

**id 13이 9/14·9/17·오늘 세 번 다 희생됐습니다.** 특정 슬롯이 반복해서 선택되고 있습니다.

## 5. ★★★ 고칠 방향 — 클라이언트 플래그를 믿지 마세요

지금 구조는 **클라이언트가 "이건 내 계획이야"라고 말하면 서버가 믿습니다.**

```
POST /api/itineraries  { id: 13, placesData: [...] }
  → 서버는 소유자만 확인하고 저장
  → 내용이 강릉이든 도쿄든 상관하지 않음
```

### ① 서버에서 막으세요

```
POST /api/itineraries 에 출처를 요구
  body.source = 'user-edit' | 'course-copy' | 'restore'
  'user-edit' 인데 Referer 가 /planner/{shareToken} 이면 거부
```

클라이언트 플래그 하나가 풀리면 끝나는 구조는 또 뚫립니다.
**서버가 마지막 방어선이어야 합니다.**

### ② 뷰어 URL과 편집 URL을 분리하세요

```
지금:  /planner/{shareToken}   ← 뷰어도 여기, 내 계획 편집도 여기
제안:  /planner/{id}           ← 내 계획 편집 (로그인 필요)
       /view/{shareToken}      ← 읽기 전용, 저장 코드 자체를 로드하지 않음
```

**"플래그로 끄기"가 아니라 "저장 코드가 없는 화면"이 확실합니다.**
같은 컴포넌트에 플래그를 얹으면 언제든 다시 켜집니다.

### ③ 저장 직전 한 번 더 확인

```
저장하려는 placesData 의 지역  vs  대상 계획에 마지막으로 저장된 지역
  다르면  →  저장 중단 + 콘솔 경고
```

도쿄 계획에 강릉이 들어가는 건 **어떤 정상 시나리오에도 없습니다.**
값싼 안전망입니다.

## 6. ★★ 재현 절차 (이걸로 검증하세요)

**20초는 부족합니다. 10분입니다.**

```
1. 로그인 후 내 계획 목록 전체를 기록
2. /api/content/courses/…/open 으로 다른 지역 코스를 연다
3. 탭을 그대로 두고 10분 대기  (백그라운드로 보냈다가 돌아오기 포함)
4. 계획 목록을 다시 기록해 1번과 대조
5. GET /api/itineraries/{각 id}/revisions 로 그 사이 저장이 있었는지 확인
```

**5번이 핵심입니다.** 내용이 우연히 같아 보여도 revision 이 늘어났으면 저장된 겁니다.

## 7. ★ 복구 기능은 잘 작동합니다

오늘 두 번 썼고 두 번 다 성공했습니다.

```
POST /api/itineraries/7/revisions/5/restore    →  200, 후쿠오카 19곳 복구 ✅
POST /api/itineraries/13/revisions/9/restore   →  200, 강릉 되돌림 ✅
shareToken 유지 ✅ ·  OG 이미지 재생성 확인 ✅
```

**이 기능이 없었으면 오늘도 수동 재구성이었습니다.** 판단이 좋았습니다.

다만 두 가지가 아쉽습니다.

```
· 개별 revision 의 내용을 읽는 API 가 없습니다
  GET /api/itineraries/{id}/revisions/{rev}  →  placesData 반환
  → 되돌리기 전에 "무엇으로 돌아가는지" 볼 수 있어야 합니다

· 되돌리기가 또 revision 을 남겨 목록이 빨리 찹니다 (정상 동작이지만)
  → 목록에 "되돌리기로 생성됨" 표시가 있으면 읽기 쉽습니다
```

| OG 이미지 | ✅ 200 · image/png · 1200×630 · 경로선이 도로를 따라감 |

### ★ OG 메타에 두 가지 오류

```
og:image:width   = 1600      실제 1200   ✗
og:image:height  = 1000      실제  630   ✗
```

**#256에서 이미지를 1200×630으로 고치면서 선언값을 안 고쳤습니다.**
카카오·트위터가 선언값으로 자리를 잡으면 잘리거나 여백이 생깁니다.

```
twitter:image = https://www.tradule.co.kr/opengraph-image     ← 기본 사이트 이미지
og:image      = https://www.tradule.co.kr/api/og/plan/….png   ← 계획 이미지
```

**twitter:image 가 계획 이미지를 안 가리킵니다.** 같은 값으로 맞춰주세요.

## 9. ★ 공유 이미지가 아직 하루치입니다

동근님이 전에 말씀하신 *"공유이미지가 하루치인 일부분밖에 안보임"* 이 그대로입니다.
후쿠오카 19곳 중 **2일차(타워·박물관·오호리·모모치)만** 그려집니다.

#256의 "대표 하루만 그리기"는 **URL 길이 8,192자 제한을 피하려던 선택**이었습니다.
의도된 동작이면 그렇다고 알려주시고, 아니면 아래를 검토해주세요.

```
· 전체 일정을 담되 경로선을 더 강하게 단순화 (simplifyPath 허용 오차 ↑)
· 또는 일자별 색을 다르게 해 전체를 한 장에 (경로선 없이 마커만)
· 또는 이미지 안에 "2일차" 라벨을 넣어 하루치임을 명시
```

**지금은 19곳 계획인데 4곳짜리로 보입니다.** 공유받은 사람이 오해합니다.
