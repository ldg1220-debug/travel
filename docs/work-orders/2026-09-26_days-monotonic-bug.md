## 1. 🔴 비단조 동작 — 1일은 안 되는데 2일은 됩니다

이게 가장 심각합니다. 유후인 실측입니다.

```
유후인 days=1  →  422   count=3    threshold=4     ❌
유후인 days=2  →  200   spots=9                    ✅
유후인 days=3  →  422   count=10   threshold=12    ❌
```

**당일치기는 거절하면서 1박2일은 만들어 줍니다.**

사용자 입장에서 설명이 불가능하고, 블로그 파이프라인은 "유후인 당일치기" 키워드에서 422를 받고 스킵합니다. 더 쉬운 요청이 더 어려운 요청보다 먼저 실패합니다.

### 원인 — 후보 수집량이 `days`에 종속돼 있습니다

`count` 값을 보면 드러납니다.

```
days=1 → 후보 3개   (슬롯이 적어 질의를 적게 함)
days=2 → 후보 9개
days=3 → 후보 10개
```

지역의 실제 스팟 풀은 고정인데, **요청 일수에 따라 후보를 다르게 모읍니다.** 그런데 threshold(`days×4`)는 일수에 정비례로 커지니, 두 곡선이 엇갈리는 구간에서만 통과합니다.

### 수정 — 후보 수집을 `days`에서 분리

```
현재   days → 슬롯 수 → 후보 수집량 → threshold(days×4)와 비교
수정   지역별로 가능한 최대 후보를 한 번 수집 (days 무관)
       → 그 풀 크기로 지원 가능 최대 일수를 역산
       → 요청 days가 그보다 크면 400 (메시지에 가능 일수 명시)
       → 이하면 풀에서 배분
```

이러면 세 가지가 동시에 해결됩니다.

- **단조성 보장** — d=N이 되면 d<N은 반드시 됨
- **캐시 효율** — 지역당 후보 풀 1개만 캐싱 (현재는 days별로 따로)
- **에러 메시지 개선** — "이 지역은 최대 2일까지 가능합니다"라고 알려줄 수 있음

### 최소 조건

전면 재구조화가 부담이면, **단조성만이라도 보장**해 주세요. 후보 수집 시 `days`와 무관하게 항상 최대치로 모으면 됩니다. threshold 공식은 그대로 둬도 됩니다.

## 2. 🔴 휴양형 7일은 현재 데이터로 불가능합니다

세부 실측입니다. 지시서가 "세부 days=7"을 대표 케이스로 잡았는데, 그게 안 됩니다.

```
세부 days=3  →  200   spots=6
세부 days=4  →  422   count=7    threshold=8
세부 days=5  →  422   count=8    threshold=10
세부 days=6  →  422   count=11   threshold=12
세부 days=7  →  422
```

**count가 threshold를 계속 한두 개 차이로 못 넘습니다.** 후보가 늘긴 하는데 기준이 더 빨리 올라갑니다.

다른 휴양지도 마찬가지입니다.

```
푸꾸옥 days=5  →  422   count=9    threshold=10     ← 한 개 차이
괌     days=5  →  200   spots=10                    ← 정확히 threshold
```

**괌이 유일하게 d=5를 통과했고, 그것도 딱 10개로 간신히입니다.**

즉 휴양지 스팟 풀이 10개 내외입니다. **상한을 7일로 올린 건 코드상 가능해졌을 뿐, 데이터가 따라오지 않았습니다.**

### 판단이 필요합니다

```
A. 휴양지 스팟 큐레이션을 먼저 늘린다
   7일 = threshold 14. 지금 10개 내외이니 지역당 최소 15개 필요
   20개 지역 × 15개 = 300개 큐레이션

B. 휴양형 threshold 공식을 낮춘다 (days×2 → days×1.5 등)
   빠르지만 같은 장소를 여러 날 반복 배치하게 됨
   §1(비단조)과 겹쳐 품질이 더 나빠질 소지

C. 휴양형 상한을 현실에 맞춰 낮춘다 (7일 → 5일)
   그래도 세부·푸꾸옥은 d=5도 안 됨
```

**A가 정답이지만 비용이 큽니다.** 당장은 §1을 고쳐서 "이 지역은 최대 N일" 메시지를 정확히 주는 쪽이 현실적입니다. 그러면 블로그가 지원 가능한 일수만 골라 쓸 수 있습니다.

## 3. 🔴 city 기준 강화 회귀 — 우려가 현실이 됐습니다

개발 세션이 "기존 통과 요청 일부가 새로 422 받을 가능성"이라고 짚은 부분입니다. **실제로 발생합니다.**

```
통영   days=3  →  200   spots=14        ✅
안동   days=3  →  200   spots=13        ✅
유후인 days=3  →  422   count=10  thr=12  ❌
호이안 days=3  →  422   count=11  thr=12  ❌
```

유후인·호이안은 이전 기준(고정 3)에서는 통과했을 요청입니다. **d=2까지는 여전히 되니(유후인 9곳 / 호이안 8곳) 완전히 막힌 건 아니지만, 3일 코스가 사라졌습니다.**

§1을 고치면 후보 수집량이 늘어 이 중 일부는 자연히 복구됩니다. **§1 수정 후 다시 측정해서 그래도 남는 지역만 별도 판단**하시는 게 순서입니다.

## 7. 처리 결과 (이 세션이 추가)

### §1 — 최소 조건으로 완료 (전면 재구조화는 하지 않음)

지시서가 명시한 "최소 조건"(전면 재구조화 대신 단조성만 보장)으로
처리했다. 코드를 직접 확인해 정확한 원인을 규명했다: `generateDay`의
1일차 LLM 재시도(`if (deduped.length < MIN_DAY0_STOPS)`)와 2일차 이후
`excludeNames` 완화 재시도(`if (crossDayDeduped.length < MIN_DAY0_STOPS)`)가
쓰던 재시도 기준이, 작업지시서 2026-09-23 "자동 코스 일수 확장"이 도입한
실제 통과 기준(`minViableSpots` — city 하루 4곳)과 완전히 분리된 옛
고정값(`MIN_DAY0_STOPS = 3`)이었다. 유후인 days=1의 결과가 정확히 3곳
이었던 것도 이 때문이다 — 3은 옛 기준(3) *미만*이 아니라서 재시도가
아예 일어나지 않았는데, 정작 진짜 통과 기준(4)에는 못 미쳐 그대로
422로 떨어졌다.

`MIN_DAY0_STOPS`를 완전히 제거하고, 이 날짜가 채워야 할 "공정한 몫"을
`minViableSpots(style, 1)`로 재정의해 양쪽 재시도 분기 모두에 적용했다
— city는 4(기존 3보다 엄격, §1이 지적한 정확한 그 지점), resort는
3(기존과 동일, 회귀 없음). threshold 공식(`minViableSpots`) 자체는
전혀 손대지 않았다 — 지시서가 명시한 범위 그대로다.

**이 세션은 라이브 API 접근이 없어 이 수정이 실제로 유후인 d=1을
통과시키는지, d=3(count=10→threshold=12)이 얼마나 회복되는지 직접
확인하지 못했다.** 재시도가 더 자주 트리거되어 각 날짜가 자기 몫에
더 잘 도달하게 되므로 개선을 기대하지만, 완전한 단조성(§5 첫 항목:
"임의 지역에서 d=N 성공 시 d<N 전부 성공")을 수학적으로 보장하지는
않는다 — 재시도도 실패하면(예: 지역 후보 풀이 정말로 얕으면) 여전히
채우지 못할 수 있다. 이 부분은 지시서 §1 "수정"(후보 풀을 days와
무관하게 한 번만 수집)의 전면 재구조화 없이는 완전히 해결되지 않는다
— 이번 라운드는 명시적으로 "최소 조건"만 이행했다.

**400 메시지에 지역별 지원 가능 최대 일수를 포함하는 것(§5 체크리스트)은
이번 최소 조건 구현으로는 처리하지 못했다** — 이는 전면 재구조화(지역별
후보 풀 크기로 최대 일수를 역산하는 것)가 있어야 가능한 기능이라,
지시서 자체도 이걸 "전면 재구조화" 쪽으로 분류했다.

### §2 — 판단 보류 (지시서가 요청한 그대로)

지시서가 명시적으로 "판단이 필요합니다"(A/B/C)로 사람의 결정을
요청했고, "당장은 §1을 고쳐서 메시지를 정확히 주는 쪽이 현실적"이라고
스스로 §1로 미뤘다. 이번 라운드는 §1만 처리했다 — §2(휴양지 큐레이션
확장/threshold 공식 조정/상한 하향) 중 어느 것도 이번에 선택하지
않았다. Cowork의 §1 재측정 이후 판단을 기다린다.

### §3 — 재측정은 Cowork 담당 (지시서가 명시)

지시서 §4가 "§1 수정 후 §3 회귀 재측정 — 제가 하겠습니다"로 명시했다.
이 세션은 라이브 접근이 없어 어차피 재측정할 수 없었고, 지시서의
역할 분담 그대로 따랐다 — 통영·안동·오사카 d=5 회귀 없음 확인과
유후인·호이안 d=3 복구 여부는 Cowork가 §1 배포 후 확인해야 한다.
