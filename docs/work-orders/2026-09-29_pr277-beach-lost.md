## 처리 결과

### §2 — 완료 (해변 보장을 마지막 단계로 이동 + 422/캐시 일관성)

`ensureResortBeachSpot` 호출을 `buildBrief`의 조립 파이프라인에서
`reallocateStopsByDay`(지리적 재배치) → `capResortSpaSpotsPerDay`(하루
스파 상한) → `redistributeThinResortDays`(하루 최소 2곳 재배분, §3-①)
전부가 끝난 뒤로 옮겼다 — 지시서 원문 "모든 필터·상한·일자 배분이 끝난
마지막 단계"를 그대로 따랐다. 정확한 원인(어느 단계가 해변을 밀어냈는지)
은 이 세션이 라이브로 재현할 수 없어 특정하지 못했지만, 해변·섬이
지리적으로 멀리 떨어져 있어 재배치 파이프라인(거리 기반 재균형·이상치
제거 포함)에 걸렸을 가능성을 코드 주석에 남겼다 — 처방(마지막 단계로
이동)이 원인 규명 없이도 문제를 구조적으로 없앤다는 점은 지시서와 같은
판단이다.

**"그래도 없으면 422"도 함께 구현했다.** `meetsResortBeachRequirement
(spots, style)`를 새로 만들어 — 스팟 수 기준(`minViableSpots`)과 같은
자리 세 곳 모두에 적용했다: `isCacheableBrief`(쓰기 경로), `isFreshBriefPayload`
(읽기 경로), `course-brief/route.ts`의 422 판정. 페이지(`page.tsx`)의
얇은 콘텐츠 판정에도 같은 함수를 추가했다 — 작업지시서 2026-09-28 §2②가
확립한 "페이지·API가 같은 기준을 쓸 것" 원칙을 그대로 따른 것으로,
스팟 수만 확인하고 해변 여부는 확인하지 않으면 똑같은 종류의 불일치
(페이지는 렌더, API는 422)가 재발할 수 있어 자발적으로 셋 다 갖췄다
(지시서가 명시적으로 요청한 범위를 넘지만, 지시서 §2 자체가 인용한
과거 원칙과 직접 연결되는 위험이라 판단해 포함했다).

### §3-① — 완료 (하루 최소 2곳 재배분)

`redistributeThinResortDays(dayGroups)`를 추가했다 — 새 후보를 검색하지
않고, 이미 확보한 스팟만 재배치한다. 스팟이 1곳뿐인 날마다, 3곳 이상
(옮겨도 2곳 이상 남는) 날 중 가장 여유로운 날에서 식사(dinner) 슬롯이
아닌 스팟 중 가장 인기(평점×리뷰수) 낮은 것을 옮긴다. `capResortSpaSpotsPerDay`
이후(스파 상한이 만든 1곳짜리 날을 대상으로 하므로)·`ensureResortBeachSpot`
이전(§2의 "마지막 단계"가 이 재배분 다음이 되도록)에 배치했다.

**알려진 한계**: 스팟 총량 자체가 부족하면(예: 여유로운 날이 하나도
없음) 일부 날은 여전히 1곳으로 남을 수 있다 — 새로 만들어내지
않는다는 원칙상 이 함수가 보장할 수 있는 건 "가진 걸 최대한 고르게
나누는 것"까지다. 실제 세부 7일 사례(3·2·2·2·4·1·1)가 이 함수로
전부 2곳 이상이 되는지는 이 세션이 라이브로 확인하지 못했다 — 단위
테스트로는 정확히 같은 분포를 재현해 모든 날이 2곳 이상이 됨을
확인했다.

### §3-② — 완료 (숙소 코스 전체 1곳)

`courseRecommend.ts`에 `isLodging(p)` 추가 — Google `primaryType`이
`hotel`/`lodging`/`resort_hotel`/`motel`/`guest_house`/`hostel`/
`bed_and_breakfast` 중 하나면 숙소로 판정한다. 이름 패턴은 쓰지
않았다 — 호텔 이름이 너무 다양해 이 코드베이스의 다른 이름 매칭보다
오탐 위험이 크다고 판단해, `isLargeFacility`처럼 타입만으로 판정하는
방식을 택했다. `courseBrief.ts`에 `capLodgingToOne(dayStops)`를 추가해
코스 전체에서 가장 인기 있는 숙소 1곳만 남기고 나머지는 뺀다(대체
없음) — `capResortSpaSpotsTotal`과 같은 자리(재배치 이전, 코스 전체
총량 캡)에서 호출한다.

### `COURSE_ALGO_VERSION` — 완료 (12→13)

§2·§3이 전부 `courseBrief.ts`의 최종 브리프 조립 로직에만 있어 원본
후보 캐시와 무관하게 이 버전에만 반영된다. 버전을 올리지 않으면 세부
d7 같은 지역이 26시간 동안 해변 없는 옛 구성을 그대로 반환하므로
13으로 올렸다.

### 검증 관련 메모

이 세션은 프로덕션 Vercel 로그·GCP 콘솔·라이브 API 호출에 접근할 수
없어, §5 표의 실측(세부 d7 해변 ≥1·하루 ≥2곳·숙소 ≤1·공항/여행사 0,
세부 d3 해변 유지, 경주·서울·방콕 회귀 없음)은 코드 검토와 단위
테스트로만 검증했다. 특히 §2에서 해변이 사라진 정확한 원인(어느
재배치/필터 단계인지)은 라이브 로그 없이는 확정할 수 없었다 — 처방이
효과가 있는지는 Cowork의 다음 실측이 확인해야 한다.
