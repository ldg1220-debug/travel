## 1. 확인 결과 — 아직 구현 안 됐습니다

`/api/feed` 응답 필드 전부입니다.

```
id, title, content, images, createdAt,
authorId, authorName, authorImage, tripTitle, region
```

**장소 데이터가 없습니다.** `itineraryId`도, `shareToken`도, `places`도 없습니다.
`tripTitle`만 있습니다.

```
후기 5  tripTitle = "5월22일 ~ 26일 후쿠오카"
후기 2  tripTitle = "0711 오사카"
후기 7  tripTitle = "7월18일 동래"
```

후기 화면에도 **"담기" / "복사" 버튼이 없습니다.**

---

## 2. ★★★ 지금 만들어도 이번 복구엔 못 씁니다

후기는 계획을 **참조만** 하고 자기 사본을 갖고 있지 않습니다.

```
후기 5  ──참조──▶  itineraries id 7  ("5월22일 ~ 26일 후쿠오카")
                            └─ 내용이 경주 코스로 덮어써진 상태
```

**그래서 지금 복사 기능을 붙이면 덮어써진 경주 코스가 복사됩니다.**
복구는 여전히 DB 시점 복구(PITR)뿐입니다.

> 그리고 이 참조 구조 때문에, 후기 화면이 계획 내용을 보여주는 부분이 있다면
> **이미 잘못된 코스를 보여주고 있을 것**입니다. 확인해 주세요.

---

## 3. ★★★ 그래서 스냅샷이 먼저입니다

이번 사고가 정확히 그 이유를 보여줍니다. **원본 계획이 바뀌면 후기도 같이
망가지는 구조**입니다. 여행 기록은 그때의 사실인데 나중 편집에 끌려다닙니다.

```
후기 작성 시점의 계획을 그대로 복사해 후기에 저장한다
```

```sql
-- reviews 테이블
coursesSnapshot  jsonb   -- 작성 시점의 placesData 전체 사본
```

| 항목 | 지금 | 변경 |
|---|---|---|
| 후기 ↔ 계획 | 참조 (제목) | **작성 시점 사본** |
| 원본 계획 수정 | 후기도 바뀜 | 후기는 그대로 |
| 원본 계획 삭제 | 후기 코스 사라짐 | 후기는 그대로 |

**참조도 같이 유지하세요** — "작성자의 최신 계획 보기"는 별도로 쓸 수 있습니다.
스냅샷은 "그때 이렇게 다녀왔다", 참조는 "지금은 이렇다"입니다.

---

## 4. ★★ 담아가기

스냅샷이 있으면 복사는 단순해집니다.

```
후기 상세
  ── 이 여행의 코스 ──
  1  캐널시티 하카타
  2  이치란 캐널시티하카타점
  …
  [내 계획으로 담아가기]
```

```
누르면:
  스냅샷을 그대로 새 계획으로 만든다 (항상 새 행 — 기존 계획 절대 수정 안 함)
  제목: "{원제목} (복사)"
  날짜: 오늘 기준으로 재배치, 시각·체류시간은 유지
  origin = "copy", sourceReviewId 기록
```

**"항상 새 행"이 핵심입니다.** 같은 지시서의 `course-open` 사고와 같은 실수를
반복하지 마세요 — 복사는 어떤 경우에도 기존 계획을 건드리면 안 됩니다.

### 비로그인 사용자

블로그에서 들어온 사람이 대부분 비로그인입니다.

```
비로그인 → 로그인 유도 후, 로그인하면 그 계획을 담아준다
(담기 의도를 세션에 보관했다가 로그인 직후 실행)
```

여기서 그냥 로그인 화면만 띄우고 끝나면 이탈합니다.
