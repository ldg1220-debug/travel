## 2. ★★★ 새 기준선에 걸려 떨어지는 지역

422 응답에 `count` / `threshold` 가 붙어 원인이 바로 보입니다. 좋습니다.

```
오사카 d2   422  7 / 8
고베   d2   422  7 / 8
경주   d3   422 10 / 12      ← 같은 시각 페이지는 11곳으로 렌더
세부   d5   422  9 / 10
세부   d7   422 13 / 14
교토   d1   422  2 / 4       ← 이건 진짜 붕괴
```

**교토를 빼면 전부 기준선에서 1~2곳 모자란 탈락입니다.**

```
도시형 기준 = days × 4   (d2=8 · d3=12)
휴양형 기준 = days × 2   (d5=10 · d7=14)
```

이 기준은 제 9/23 지시서에서 나왔습니다. 다만 거기서 **"후보 풀을 일수에 맞게 먼저 늘리고"** 그 다음 기준을 올리라고 했는데,
**기준만 먼저 올라가고 후보 풀 확장(A-2)은 아직입니다.** 그래서 어제까지 200 이던 경주 2박3일이 오늘 422 입니다.

### 오락가락합니다

```
경주 d3  API 호출  → 10곳 → 422
경주 d3  페이지    → 11곳 → 렌더됨
```

**생성마다 곳수가 1~2개씩 다르고, 그게 기준선 바로 위아래라 결과가 뒤집힙니다.**
AutoPipeline 은 API 를 쓰므로 같은 키워드가 어떤 때는 되고 어떤 때는 스킵됩니다.

### 고칠 것

```
① A-2(후보 풀 일수 분리) 전까지 도시형 기준을 days × 3 으로
     d2=6 · d3=9 · d4=12 · d5=15
② 페이지와 API 가 같은 판정 함수를 쓰게
     (지금은 페이지가 11 < 12 인데도 렌더)
③ 422 도 캐시하지 않는지 재확인
     (실패가 캐시되면 기준을 고쳐도 26시간 동안 그대로)
```

**①은 되돌리는 게 아니라 순서를 맞추는 것입니다.** A-2 가 들어오면 ×4 로 올리세요.

## 3. ★★★ 휴양형 "구성"이 빠졌습니다

9/23 지시서 §4 에서 휴양형은 **하루 스팟 수뿐 아니라 후보 구성**을 바꾸라고 했습니다.

```
후보 구성:  액티비티(호핑·스노클링·다이빙·투어) · 해변 · 스파/마사지 · 선셋 · 야시장 · 맛집
하루 동선:  숙소권 반경 안 위주, 멀리 가는 날 하루만
```

지금 세부 d3 입니다.

```
d1  마젤란의 십자가(관광지) → 산 페드로 요새(기타) → La Parisienne Cebu(음식점)
d2  House of Lechon(음식점) → Cabana Restaurant(음식점)
d3  레아신전(관광지)

음식점 3 · 관광지 2 · 기타 1 · 액티비티 0 · 해변 0 · 스파 0
하루 3 · 2 · 1 곳
```

**하루 곳수만 휴양형으로 줄었고, 내용은 세부시티 도시 관광 그대로입니다.**
막탄 리조트권, 호핑투어, 해변이 하나도 없습니다. 3일차는 레아신전 한 곳뿐입니다.

```
"하루 2~3곳" 은 결과이지 목표가 아닙니다.
휴양형은 후보 카테고리부터 바꿔야 합니다:
  카테고리 슬롯   tour/activity · beach · spa · 음식점 · (선택) 관광지
  하루 구성       액티비티 1 + 식사 1~2  또는  휴식일(스파·해변·카페)
  앵커            리조트 권역(세부 = 막탄) 좌표
```

**이게 안 되면 휴양형 7일은 "세부시티 관광지를 7일에 나눠 담은 코스" 가 됩니다.**

## 처리 결과

### §2① — 완료 (도시형 기준 days×3)

`src/lib/server/courseBrief.ts`의 `minViableSpots`에서 도시형 계수를
4→3으로 낮췄다(`const perDay = style === "resort" ? 2 : 3;`). 지시서
표현 그대로 "되돌리는 게 아니라 순서를 맞추는 것"이며, A-2(후보 풀을
일수에 맞게 먼저 늘리는 작업)가 들어오기 전까지의 임시 조치라는 점을
docstring에 남겼다. 관련 테스트(`courseBrief.test.ts`의
`minViableSpots`/`isCacheableBrief`/`isFreshBriefPayload` describe
블록)를 새 계수에 맞게 갱신했다 — days=1에서는 도시(3)·휴양(3)이 같은
값이 되어 구분이 안 되므로, 두 스타일이 갈리는 days=2 기준으로 다시
작성했다.

### §2② — 완료 (페이지·API 판정 통일)

`src/lib/coursePages.ts`의 `isCourseBriefThin`이 내부에 5를 하드코딩하고
있어 API(`minViableSpots` 기준)와 페이지가 서로 다른 기준으로 "얇음"을
판정하던 것이 지시서가 지적한 "11 < 12인데도 렌더"의 정확한 원인이었다.
`isCourseBriefThin(spots, minSpots: number)`로 시그니처를 바꿔 순수
함수로 유지하고(이 파일은 "use client" 컴포넌트에서 임포트되므로
서버 전용 Postgres pool을 끌고 오는 `courseBrief.ts`의 값을 직접
import할 수 없다 — 파일 자체의 기존 제약), 실제 임계값 계산은 서버
컴포넌트인 `src/app/(app)/course/[region]/[days]/page.tsx`에서
`minViableSpots(styleForRegion(region), days)`로 넘기게 했다.

### §2③ — 완료 (422 미캐시 재확인, 코드 변경 없음)

`isCacheableBrief`와 `isFreshBriefPayload`(둘 다 courseBrief.ts) 코드를
직접 읽어 확인한 결과, 이번 라운드 이전부터 이미 `minViableSpots`를
써서 임계값 미달 결과를 캐시하지 않고 있었다 — §2①에서 계수를 낮춘
효과가 캐시 TTL(26시간)을 기다리지 않고 바로 반영된다. 새로 만들 코드가
없었다.

### §3 — 부분 완료 (카테고리 버그만 수정, 리조트 앵커는 보류)

`src/lib/server/courseRecommend.ts`의 `THEME_SLOTS.resort` /
`THEME_SLOT_TEMPLATES.resort`에서 `activity`·`relax` 슬롯에 걸려 있던
`category: "attraction"`을 제거했다(`dinner` 슬롯의
`category: "restaurant"`는 유지). 코드를 읽어 확인한 실제 버그 두 가지:
(1) 이 값이 Google Places `includedType`으로 그대로 들어가
`tourist_attraction`을 하드 필터로 걸어 투어/스파 업체를 배제하고
있었고, (2) `CATEGORY_LABEL.attraction`("관광명소")이 검색 질의 문장에
그대로 붙어 검색어 자체를 관광명소 쪽으로 밀고 있었다 — 지시서가
관찰한 "세부 d3가 세부시티 관광지 그대로"인 현상과 정확히 일치한다.
회귀 테스트를 `courseRecommend.test.ts`에 추가했다.

**"리조트 권역 앵커"(세부 → 막탄 좌표로 검색 중심 이동)는 이번
라운드에서 다루지 않았다.** 이 세션은 라이브 Google Places 응답을 볼
수 없어, 좌표를 어디로 얼마나 옮겨야 실제로 막탄 리조트권 후보가
잡히는지 확인 없이 값을 정하는 건 근거 없는 추측이 된다. 카테고리
버그(위)만으로도 액티비티/스파 카테고리 자체가 검색에 다시 포함되므로
효과 일부는 기대되지만, "세부 = 막탄"처럼 지역마다 앵커 좌표를 매핑하는
작업은 실측 데이터로 검증 가능한 다음 라운드로 넘긴다.

### §4 — 진단 로깅만 추가 (원인 미확정)

`fetchSlotCandidates`(courseRecommend.ts)의 캐시 미스(콜드) 경로에
`console.log`를 추가해, Google 호출 직후 원본(raw) 개수·`isValidPlace`
통과(valid) 개수·품질 게이트(평점·리뷰수) 통과(gated) 개수를 지역/도시/
슬롯 키워드/카테고리와 함께 남기게 했다. 지시서가 요청한 "슬롯별 반환
개수 · 필터에서 몇 개가 빠졌는지"에 정확히 대응한다 — raw가 이미 작으면
검색 자체(질의·타입 제한) 문제, gated가 raw보다 뚜렷이 작으면
평점/리뷰수 하한 문제라는 걸 다음 Vercel 로그 확인에서 구분할 수 있다.

**교토 d1이 실제로 어느 쪽 문제인지는 이 세션이 확인하지 못했다** — 이
세션은 프로덕션 Vercel 로그에 접근할 수 없어, 추가한 로그가 실제로
찍히는 걸 보지 못한 채 코드만 넣었다. 다음 라운드에서 로그를 확인해
알려주시면 원인(질의/타입 제한 vs. 평점·리뷰수 하한 vs. 거리·중복·브랜드
필터)에 맞는 수정으로 이어갈 수 있다.

### §5 (`#274` 검증) — 이번 라운드 작업 대상 아님

지시서 §5는 확인 결과 보고이지 요청 사항이 아니어서 별도 처리하지
않았다. 429/403/400 등 정확한 실패 상태코드 확인과 GCP 일일 호출 상한
확인은 이 세션이 Vercel/GCP 콘솔에 접근할 수 없어 여전히 할 수 없다.

### §6-4 (A-2, 후보 풀 일수 분리) — 이번 라운드에서 다루지 않음

지시서 자체가 순서표(§6)에서 4번째(최후순위)로 배치했고, city×3 임시
계수(§2①)가 A-2 완료 전까지의 잠정 조치임을 명시하고 있어 이번
라운드에서는 손대지 않았다. A-2가 들어오기 전까지는 city 계수를 4로
올리지 말 것 — 이 지시서의 명시적 지시.
