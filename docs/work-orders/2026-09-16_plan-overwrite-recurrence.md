## 2. 서버는 막혀 있는데 뚫렸습니다

`#251`의 부분 유니크 인덱스는 정상 동작합니다 — 제가 9/14에 확인했습니다.

```
course-open 2회 호출  →  계획 수 불변, 사용자 계획 무변  ✅
```

**그때 검증한 건 서버의 INSERT 경로뿐입니다.**
이번에 뚫린 건 그 경로가 아닙니다.

### 추정 — 플래너가 "마지막으로 보던 계획 id"를 물고 저장합니다

```
1. 블로그 CTA(course-open) 클릭
2. 플래너가 콘텐츠 코스를 화면에 로드
3. 그런데 플래너의 로컬 상태에는 직전에 열었던 내 계획 id 가 남아 있음
4. 저장(수동/자동)이 일어나면서 POST /api/itineraries { id: 내_계획_id, placesData: 코스 }
5. 내 계획이 코스로 덮임
```

`POST /api/itineraries`는 **`id`가 오면 그 행을 그대로 갱신합니다.**
서버 입장에선 정상 요청이라 막을 방법이 없습니다.

> `id=4`가 `id=7`의 내용을 갖게 된 것도 같은 방식으로 설명됩니다 —
> 다른 계획을 보던 중 저장이 일어나 id가 어긋난 것으로 보입니다.

## 3. ★★★ 수정

### ① 남의 계획·콘텐츠 계획은 **뷰어 모드**로

```
/planner/{shareToken} 이 내 소유가 아니면
  · 로컬 "현재 계획 id" 를 건드리지 않는다
  · 편집·저장 경로를 아예 비활성화한다
  · 쓸 수 있는 건 "내 계획으로 담아가기" 뿐
```

**지금은 남의 계획을 열면 그게 내 작업 공간이 됩니다.** 그게 근본 원인입니다.

### ② 저장 시 id 소유·일치 확인

```
POST 직전에:
  저장하려는 placesData 의 출처(로드한 계획의 id/shareToken)와
  보내려는 id 가 같은지 확인한다. 다르면 보내지 않는다.
```

### ③ 서버 쪽 방어

```
POST /api/itineraries 에 origin 확인 추가
  · origin='content' 또는 'copy' 인 행은 이 경로로 갱신 불가
  · 갱신 시 이전 placesData 를 itinerary_revisions 에 남긴다 (되돌리기용)
```

**③의 revisions가 있었으면 오늘 복구가 30초면 끝났습니다.**
지금은 이력이 없어 원본을 영영 못 되살립니다.
