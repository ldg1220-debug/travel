## 1. 제 §2 진단이 틀렸습니다 ★

지시서에 **"같은 장소인데 화면이 네 개"** 라고 썼습니다.
세션이 "이미 하나의 공유 컴포넌트(`PlaceDetailOverlay`)였다"고 반박했는데,
**세션 쪽이 맞습니다.**

진짜 원인은 컴포넌트가 아니라 **데이터**였습니다.
`해유관`을 검색하면 구글이 **서로 다른 장소 두 개**를 돌려줍니다.

```
ChIJzakNjPToAGARzCwIriDFg28   aquarium            ★4.5 · 리뷰 61,276
ChIJc34jawDpAGARgbfIM07_DnA   tourist_attraction  평점·리뷰 없음
```

**이름도 주소도 같고, 좌표만 170m 떨어져 있습니다.**

동근님이 테마파크에서 누른 것은 위(풍부한) 레코드,
관광지에서 누른 것은 아래(빈) 레코드였습니다.
같은 컴포넌트가 **서로 다른 데이터**를 받아 다르게 보였던 것입니다.

## 2. ★★★ 그래서 #244의 중복 제거가 역효과입니다

`dedupeIntoPriorityBuckets()`는 **버킷 우선순위**로 남길 것을 고릅니다.
`LIVE_BUCKET_GROUPS` 순서상 **관광지가 테마파크보다 앞**입니다.

```
관광지(tourist_attraction, 평점 없음)   ← 남음
테마파크(aquarium, ★4.5 리뷰 61,276)    ← 버려짐
```

배포 후 실측입니다.

```
관광지 2
  해유관      1-chōme-1-10 Kaigandōri …
              실제 지도 데이터            ← 평점 자리가 비어 있음
  大阪港      4.7 · 리뷰 72
테마파크 1
  덴포산 하버 빌리지   4.3 · 리뷰 1.9k
```

**중복은 사라졌는데, 남은 쪽이 빈 레코드입니다.**
이전에는 최소한 테마파크 경로로 들어가면 리뷰를 볼 수 있었는데 이제 그 길이 없습니다.

## 3. 수정 — 버킷이 아니라 "정보가 많은 쪽"을 남기세요

```js
// dedupeIntoPriorityBuckets 안에서, 같은 이름 그룹을 고를 때
1순위: rating·reviewCount 가 있는 레코드
2순위: 그래도 동률이면 사진 개수가 많은 쪽
3순위: 그래도 동률이면 기존대로 버킷 우선순위
```

**표시 위치는 지금대로 우선순위 버킷에 두되, 내용은 풍부한 레코드를 쓰세요.**
즉 `해유관`은 **관광지 섹션에 남기고, 데이터는 `aquarium` 레코드**를 씁니다.

### 이름만으로 묶는 건 위험합니다

지금은 이름(공백·대소문자 무시)만 봅니다.
**이름이 같아도 다른 장소인 경우**(체인점 등)가 있으니 조건을 하나 더 거세요.

```
이름이 같고  +  좌표가 300m 이내   → 같은 장소로 묶는다
```

`해유관` 두 레코드는 170m라 이 조건에 들어옵니다.
