## 0. 진단은 맞습니다. 제안 ①만 방향을 바꿔야 합니다

원인 ①(버전 올릴 때마다 전체 캐시 무효화), ②(새 지역·일수 조합 한꺼번에 추가), 증폭 요인(평점 필드 때문에 Enterprise 등급 과금) — 세 가지 모두 맞습니다.

버전을 자주 올린 데는 제 지시서 책임도 있습니다. "구버전 캐시를 미스로 처리", "캐시 신선도 검증" 같은 요청을 라운드마다 드렸고, 그게 전부 전체 무효화로 이어졌습니다.

### 제안 ①(Basic으로 검색 → 선택된 곳만 상세 조회)은 비용이 오히려 늘어날 수 있습니다

Google 공식 문서 기준입니다.

> Text Search (New)는 **요청 1회당**, 필드마스크에 넣은 필드 중 **가장 비싼 등급**으로 과금됩니다.

즉 "후보 20곳을 비싼 필드로 조회"해도 **요금은 요청 1건분**입니다. 후보 수가 아니라 요청 수에 비례합니다.

제안 ①대로 바꾸면 이렇게 됩니다.

```
현재   Text Search(Enterprise) 1회                          = 슬롯당 요청 1건
제안①  Text Search(Pro) 1회 + Place Details(Enterprise) 4~5회 = 슬롯당 요청 5~6건
```

Pro와 Enterprise의 1,000건당 단가 차이는 크지 않습니다(참고: Pro 약 $32, Enterprise 약 $35). **몇 달러 아끼려고 요청 수를 5~6배로 늘리는 구조**가 됩니다. 게다가 평점으로 후보를 고르는 로직이 있다면, 평점 없이 먼저 고른 뒤 상세 조회하는 순서 자체가 선정 품질을 떨어뜨립니다.

**제안 ①은 하지 말아 주세요.** 대신 아래처럼 **요청 수 자체를 줄이는** 쪽이 효과가 큽니다.

## A-1. Places 원본 응답 캐시를 코스 캐시와 분리 — 효과 가장 큼

지금은 `COURSE_ALGO_VERSION`이 캐시 키에 들어가 있어서, 알고리즘을 조금만 바꿔도 **Google에 다시 물어봅니다.** 알고리즘이 바뀌어도 Google이 돌려주는 장소 목록은 그대로인데도 그렇습니다.

```
현재   (지역, 일수, 알고리즘 버전) → 코스 결과   ← 버전 바뀌면 Google 재호출

수정   1층: (검색어) → Places 원본 응답          ← 알고리즘 버전과 무관
       2층: (지역, 일수, 알고리즘 버전) → 코스 결과  ← 1층에서 다시 계산, Google 호출 없음
```

이러면 앞으로 버전을 올려도 **Google 비용이 0입니다.** 코스 계산만 다시 합니다.

**Google 약관상 저장 가능한 항목·기간에 제한이 있습니다.** 장소 ID는 계속 보관할 수 있지만 좌표·평점 등은 보관 기간 제한이 있으니, [Places API 정책 페이지](https://developers.google.com/maps/documentation/places/web-service/policies)를 확인해 1층 캐시 유효기간을 그 안으로 잡아 주세요.

## A-2. 후보 수집을 일수와 분리 — 이전 지시서와 같은 작업

이전 지시서의 "후보 수집을 일수에서 분리"가 **비용 절감에도 그대로 해당합니다.**

```
현재   오사카 d1, d2, d3, d4, d5 → 각각 따로 검색 (조합마다 슬롯 질의 반복)
수정   오사카 → 1번만 검색 → d1~d5 는 그 풀에서 배분
```

지역당 검색이 최대 5~7배 줄고, 그동안 문제였던 단조성·비결정성도 같이 풀립니다. A-1과 합치면 **1층 캐시 키가 (지역) 단위**가 됩니다.

## A-3. `COURSE_ALGO_VERSION` 운영 규칙

A-1이 들어가면 버전을 올려도 Google 비용은 안 나가지만, 콜드 재계산 시간 문제는 남습니다.

- 작은 수정마다 올리지 말고 모아서 반영
- 특정 지역만 문제면 그 지역 캐시만 삭제
- 올릴 때는 SEO 페이지 조합부터 사전 재생성 (이전 지시서 A-3)

## A-4. `/api/places/search` 캐시 + 중복 호출 제거

수동 검색창이 캐시 없이 요청 1번에 Google 호출을 2개 이상 병렬로 보낸다는 부분입니다.

- 같은 검색어 결과 캐시 (보관 기간은 A-1과 같은 기준)
- 병렬 2건이 꼭 필요한지 확인 — 하나로 합칠 수 있으면 합치기
- 필드마스크는 화면에 실제로 쓰는 필드만 (평점을 안 보여준다면 빼서 Pro 등급으로)

## A-5. 사진 조회 확인

`photos` 필드는 사진 참조값만 받는 것이고, **실제 사진 이미지를 가져오는 호출은 별도 과금**(Place Details Photos)입니다. 후보 전체의 사진 이미지를 미리 가져오는 코드가 있는지 확인해 주세요. 있다면 최종 선택된 장소에서, 화면에 보일 때만 가져오게.

## A-6. 호출 실패 로그 + 실패 결과 캐시 금지 (이전 지시서 A-1 유지)

동근님이 Google 콘솔에 일일 호출 상한을 걸 예정입니다. 상한에 닿으면 Places가 실패하는데:

- 실패 시 상태코드를 `console.error`로 남기기
- 실패하거나 후보가 비정상적으로 적은 결과는 **캐시하지 않기**
- 사용자 응답은 422 대신 "잠시 후 다시 시도" 성격의 응답(503 등)으로 구분

지금 해외가 전부 `count=2`인 것도 한도·결제 문제로 Places가 실패했을 가능성이 있습니다. 로그가 있어야 확인됩니다.

### A-6 — 완료 (최우선 항목)

  `!res.ok`일 때 상태코드·응답 본문(500자까지)을 `console.error`로
  남기도록 고쳤다. 429(쿼터)·403(키 권한)·400(질의 오류)을 다음

- **실패 결과 캐시 금지**: 코드를 확인한 결과 **이미 두 겹으로 되어

- **422 vs 503 구분 (신규 구현)**: "실패해서 얇아진 결과"와 "그 지역이
  원래 얇은 것"을 구분하기 위해, 이번 코스 생성 중 실제로 Places
  호출이 실패했는지를 요청 스코프로 추적하는 콜백(`onCandidateFetchFailure`)을
  `googleTop` → `fetchSlotCandidatesLive`/`fetchSlotCandidates`
  (courseRecommend.ts) → `generateCourseV2`의 `GenerateCourseOptions`
  (courseRecommendV2.ts) → `generateDay`/`buildBrief`(courseBrief.ts)까지
  전부 스레딩했다. **프로세스 전역 상태(모듈 레벨 플래그)는 쓰지
  않았다** — Vercel 서버리스 인스턴스마다 별개라 신뢰할 수 없기
  때문이다(값을 매번 새 콜백으로 만들어 요청 하나의 실행 범위 안에서만
  유효하다). `buildBrief`의 기존 "실패해도 절대 던지지 않는다"는 계약은
  그대로 유지했다 — 새 판단(실패 추적 + 임계값 확인 + 필요시 throw)은
  `getCourseBrief`가 한다. `dedupeInFlight`로 동시 요청이 합쳐질 때도
  판단이 한 번만(공유되는 Promise 안에서) 일어나도록 구조를 짰다 —
  추적용 변수를 `dedupeInFlight`의 `run()` 클로저 바깥에 두면 실제로

  뻔했다.
  - 새 에러 타입 `TransientApiFailureError`(courseBrief.ts) — 이번

### A-1 — 이미 상당 부분 구현돼 있음을 확인 (새로 만들지 않음) ★★★ 중요

**지시서의 핵심 전제("현재는 버전이 바뀌면 Google을 다시 부른다")를
코드로 직접 확인한 결과, 이미 아니었다.** `courseRecommend.ts`에
`place_candidate_cache`라는 원본 검색 결과 캐시가 이미 존재하고
(TTL 7일), 그 캐시 키(`candidateCacheKey`)는 **`scope:city:keyword:category`
뿐이고 `COURSE_ALGO_VERSION`을 포함하지 않는다.** 즉:

```
실제 구조 (이미 구현돼 있었다)
  1층: place_candidate_cache — (scope, city, keyword, category) → Places 원본 결과, TTL 7일, 버전 무관
  2층: content-brief 캐시 — (scope, region, days, 버전) → 최종 코스, 버전 바뀌면 무효화

  버전을 올려도 1층이 살아있으면(7일 이내 같은 도시·키워드로 조회한 적 있으면)
  2층 재계산은 1층 캐시를 히트해 Google을 다시 안 부른다.
```

`courseRecommendV2.ts`의 기존 주석(2026-09-06 이전, 이번 세션이 쓴 게
아님)도 이를 명시적으로 확인해준다: "스팟 후보 조회 자체는
candidateCacheKey가 애초에 scope:city:slot 기준이라 dayIndex 무관하게
이미 캐시 공유 중이라 재조회가 원인이 아니었다" — 정확히 이 지시서가
가정한 것과 반대되는, 이미 검증된 사실이 코드 주석에 남아 있었다.

**그래서 이번 라운드에서 "1층/2층 분리"를 새로 만들지 않았다** — 이미
있는 걸 다시 만드는 건 낭비이고, 자칫 경쟁하는 두 번째 캐싱 레이어를
만들 위험이 있었다.

**그렇다면 실제 비용 급증의 원인은 무엇인가**: 이 세션의 판단으로는,
버전 상승 자체가 아니라 **①과 ②가 결합**된 결과다 — 새 지역(필리핀·
인도네시아·싱가포르·말레이시아 등)과 새 테마(이번 주 추가한 `resort`
테마의 키워드 "액티비티 투어"·"스파 마사지"·"야시장 맛집")는 이
1층 캐시에 **한 번도 들어간 적이 없는 완전히 새로운 (city, keyword)
조합**이다 — 이런 조합은 버전과 무관하게 처음 한 번은 반드시 Google을
불러야 한다. 여기에 더해, 3일차 이상(`WIDEN_POOL_FROM_DAY_INDEX=2`)에
켜지는 `extraQuery`(동의어 2차 검색)는 **별도의 `:x2` 캐시 키**를 쓰므로
(같은 파일 `candidateCacheKey` 참고), 3일 이상 요청이 새로 생긴 지역·
테마에서는 슬롯당 최대 2건(기본 + `:x2`)의 신규 호출이 필요하다 — 이건
지시서 A-2가 지적한 것과 비슷한 결이지만, "매번 다시 검색"이 아니라
"새로운 캐시 키 표면이 늘었다"는 게 더 정확한 설명이다.

이 정정이 A-2·A-3의 실제 범위에도 영향을 준다 — 아래 참고.

### A-2 — 이번 라운드에서 다루지 않음 (범위 재정의 필요)

A-1의 발견 때문에 A-2("후보 수집을 일수와 분리")의 실제 효과 범위가
지시서가 가정한 것보다 작을 가능성이 크다 — 같은 날짜·같은 키워드는
이미 캐시로 묶여 있다. 진짜 개선 여지는 `:x2`(extraQuery) 변형 캐시를
기본 풀과 통합해 슬롯당 최대 1건으로 줄이는 것인데, 이건
`courseRecommendV2.ts`의 핵심 후보 수집 로직을 건드리는 작업이라(이
파일은 이 세션 내내 "라이브 검증 없이 손대지 않는다"는 원칙을
지켜온 공유 함수다) 신중한 별도 라운드가 필요하다고 판단해 이번엔
보류했다. 이전 지시서("비단조 버그")가 요청한 전면 재구조화(지역별
후보 풀을 days와 무관하게 한 번만 수집해 최대 지원 일수를 역산)도
같은 이유로 계속 보류 상태다.

### A-3, A-4, A-5 — 이번 라운드에서 다루지 않음

시간·컨텍스트 제약으로 A-6(최우선)에 집중했다. A-3(버전 상승 운영
규칙 문서화)·A-4(`/api/places/search` 캐시)·A-5(사진 조회 확인)는
다음 라운드로 넘긴다. 다만 A-5에 대해 간단히 확인한 것: courseBrief.ts의
`googleToPlace`는 `photos?.[0]?.name`(참조값만)을 저장할 뿐, 실제
이미지를 미리 내려받는 코드(Place Details Photos 호출)는 이번 조사
범위(`courseRecommend.ts`/`courseBrief.ts`)에서는 보이지 않았다 —
다만 `src/app/api/discover/spot-photo/route.ts` 등 사진 표시 전용
