## 5. ★★ 미지원 응답에 대안을 담아주세요

지금은 이렇습니다.

```
GET /api/content/course-brief?region=코타키나발루&days=2
  →  404  { "error": "unsupported_region" }
```

받는 쪽이 할 수 있는 게 없습니다. 이렇게 주세요.

```json
{
  "error": "unsupported_region",
  "query": "코타키나발루",
  "suggestions": [
    { "name": "냐짱",   "parent": "베트남", "reason": "동남아 해변" },
    { "name": "다낭",   "parent": "베트남", "reason": "동남아 해변" },
    { "name": "방콕",   "parent": "태국"   }
  ]
}
```

**AutoPipeline 이 "대신 이건 어떠세요"를 바로 보여줄 수 있습니다.**
지금은 그쪽에서 자체 목록으로 추측해야 합니다.

### 별칭도 받아주세요

```
나트랑 → 냐짱      호치민 → 호찌민      타이페이 → 타이베이
```

**사용자가 쓰는 표기와 공식 표기가 다릅니다.** `aliases` 를 지역 데이터에 넣어주세요.

## 9. 처리 결과 (이 세션이 추가)

### §4 — 커버리지 갭은 코드 데이터 추가로 안전하게 메울 수 있었다

처음엔 "대"(큰) 규모라 이 세션에서(라이브 API 접근 없이) 처리하기 위험하다고
판단했다 — 큐레이션된 스팟(실측 평점·리뷰수)을 새로 만드는 일이라면 그게
맞다. 하지만 코드를 추적해보니 `discoverData.ts`의 `OVERSEAS_LOCALITY_NAMES`
(=`isSupportedRegion`이 통과시키는 목록)은 실제 스팟 카탈로그뿐 아니라
`WORLD_CITIES`(좌표만 있는 "지원 대상" 목록 — 스팟이 0개여도 라이브
Google/Kakao 검색이 대신 채운다, discoverData.ts 자체 주석 참고)의
합집합이다. **즉 도시 좌표만 정확히 추가하면, 실제 장소 데이터는 이미
있는 라이브 생성 파이프라인이 그때그때 만든다** — "발리 사고"의 재발
방지 장치(`looksLikeMismatchedOverseasResult`, 한반도 좌표 가드)도 이미
모든 해외 요청에 범용으로 걸려 있어 새로 추가할 필요가 없었다. 그래서
1~6순위를 전부 이번 라운드에 넣었다:

- 필리핀(세부·보라카이·마닐라·팔라완), 인도네시아(우붓·쿠타·스미냑·자카르타),
  싱가포르, 말레이시아(코타키나발루·쿠알라룸푸르·페낭), 괌·사이판(미국
  소속으로 — 홍콩·마카오가 중국 소속으로 들어가 있는 기존 방식과 동일),
  치앙마이(태국)를 `WORLD_CITIES`에 추가했다.
- **"발리" 자체는 추가하지 않았다** — 지시서도 지적한 사고 지역이라,
  모호한 상위 지명 대신 구체적인 동네(우붓·쿠타·스미냑)만 넣었다 —
  이름이 구체적일수록 국내 동명 지역과 오매칭될 확률이 낮다.
- 좌표는 전부 공개된 도시 중심 좌표다(위도·경도) — 평점·리뷰수 같은
  장소 단위 데이터는 지어내지 않았다.

### §5 — suggestions와 별칭을 추가했다 (별칭 하나는 지시서와 반대 방향)

`/api/content/course-brief`가 `unsupported_region` 404를 줄 때
`suggestions`(이미 안정적으로 검증된 해외 지역 5곳 고정 목록)를 같이
준다 — 질의어에 맞춰 똑똑하게 고르는 대신(그럴 만한 지역·테마
taxonomy가 아직 없다), "확실히 되는 대안"을 항상 준다. `reason` 필드는
넣지 않았다 — 근거 없는 카테고리 태그를 지어내고 싶지 않았다.

별칭(`REGION_ALIASES`, `resolveRegionAlias`)을 `getCourseBrief`(course-brief
API + 워밍 크론의 공통 진입점) 맨 앞에서 적용한다. 세 개 중 둘(나트랑→냐짱,
타이페이→타이베이)은 지시서 그대로다. **"호치민 → 호찌민"은 반대로
뒤집었다** — 실제로 이 카탈로그의 실측 스팟(통일궁·노트르담 대성당 등)이
이미 "호치민"이라는 이름으로 저장돼 있고, "호찌민"은 이 파일 어디에도
없었다. 지시서 예시를 그대로 따랐다면 이미 잘 동작하던 "호치민"을
존재하지 않는 이름으로 리다이렉트해 오히려 깨뜨렸을 것이다. 이 과정에서
"호치민"이 `CITY_SEEDS`에 정의는 돼 있었지만 그 배치 전체가
`UNVERIFIED_GENERATED_SPOT_IDS` 필터에 걸려 실제로는 스팟이 하나도
안 남아 있었다는 것도 발견해 — `WORLD_CITIES`에도 좌표를 추가해 별칭의
목적지 자체가 미지원이 되는 모순을 없앴다.

### §6 — popularity는 지시서가 실제로 인용한 국가만 채웠다

`FlatRegion`에 `aliases?`/`popularity?`를 추가했다. `popularity`는
지시서 §2가 인용한 2026년 한국인 출국 순위(공개 통계)의 **순서만**
반영한다 — 정확한 방문자 수까지는 주장하지 않고, 지시서가 다루지 않은
국가(아프리카·남미 등)는 값을 아예 안 채운다(추정 금지).

### §4 — "발리 사고" 재발 방지 확인

지시서가 요청한 "좌표·국가 경계 검증"은 이미 `resolveScope`(오직
`OVERSEAS_LOCALITY_NAMES`에 있는 이름만 overseas로 분류)와
`looksLikeMismatchedOverseasResult`(overseas 스코프인데 실측 좌표가
전부 한반도 안이면 UnsupportedRegionError)로 범용 적용되고 있어, 이번에
추가한 지역들도 자동으로 그 가드를 받는다 — 새 코드를 추가하지 않았다.

### 검증 못 한 것

이 세션엔 실제 Kakao/Google Places API·DB 접근이 없어, 새로 추가한
지역(세부·우붓·싱가포르·코타키나발루 등)에서 실제 라이브 생성이
`insufficient_spots` 없이 성공하는지는 직접 확인하지 못했다 — 좌표
자체의 정확성만 검증했다(공개적으로 알려진 도시 중심 좌표). 배포 후
Cowork의 §8 확인이 이 부분의 실제 검증이다.
