## 1. ★★★ 404 — 결정적 단서를 잡았습니다

요청하신 대로 **캐시 없는 지역**을 days=3 으로 직접 호출했습니다.

```
경주   d3  →  200 · 12곳 ·  19.8km  (  1,032ms)   ← 캐시 적중
가평   d3  →  200 · 13곳 ·  88.8km  ( 13,532ms)   ← 캐시 미스, 라이브 생성
파주   d3  →  200 · 15곳 ·  83.1km  ( 11,725ms)   ← 캐시 미스, 라이브 생성
오이타 d3  →  200 ·  8곳 ·  27.2km  ( 13,815ms)   ← 캐시 미스, 라이브 생성
```

**캐시 미스 시 라이브 생성은 11~14초 걸립니다.** 그리고 정상 동작합니다.

그런데 페이지는 이렇습니다.

```
/course/경주/2박3일  →  404 · 1,235ms
```

```
API   캐시 미스  →  13초  →  200
페이지            →  1.2초  →  404
```

**페이지는 생성을 시작조차 하지 않습니다.**
`getCourseBrief` 를 부른다면 최소 몇 초는 걸려야 합니다. 1.2초는 **생성 이전 단계에서 반환**됩니다.

`maxDuration=60` 이니 시간 초과도 아닙니다. #264 의 전체 에러 캐치로도 안 잡혔습니다.

### 그러니 여기를 보세요

```
loadEnabledCourseBrief() 가 getCourseBrief() 를 부르기 전에
무언가를 확인하고 즉시 notFound() 로 떨어집니다.
```

```
① ENABLED_COURSE_PAGES 조회 — "경주"·"2박3일" 이 목록에 있다고 판정됩니까
     sitemap 생성기는 같은 목록으로 24개를 만들어냈습니다
② URL 세그먼트 디코딩 — params.region 이 "경주" 입니까, "%EA%B2%BD%EC%A3%BC" 입니까
     한글 세그먼트가 디코딩 전 문자열로 비교되면 항상 불일치합니다
③ days 세그먼트 파싱 — "2박3일" → 3 변환이 이 경로에서도 됩니까
```

**②가 가장 의심스럽습니다.** 1.2초 안에 끝나는 동기 비교 실패의 전형입니다.

```
console.log 를 notFound() 직전이 아니라 함수 진입 직후에 넣으세요.
  params.region 의 원본값 · 디코딩값 · 목록 조회 결과
```

**#264 는 `getCourseBrief` 가 던지는 에러를 잡았는데, 애초에 거기까지 안 갑니다.**

## 2. ★★★ 오사카 d2 — 구조적입니다

요청하신 반복 호출입니다.

```
오사카 d2  #1 → 422 count:2
오사카 d2  #2 → 422 count:2
오사카 d2  #3 → 422 count:2
오사카 d2  #4 → 422 count:2
```

**4회 전부 동일합니다. 예산·타이밍 문제가 아닙니다.**

일수별로 펼쳐봤습니다.

```
          d1          d2          d3
다낭      5곳         10곳        16곳       ✅ 단조 증가
방콕      7곳         12곳        13곳       ✅
오사카    5곳          2곳(422)    8곳       ✗ d2 에서 급감
교토      2곳(422)     6곳        13곳       ✗ d1 에서 급감
도쿄       —           3곳         —        ✗
경주      6곳          9곳        12곳       ✅
여수       —           8곳         —        ✅
```

**일수가 늘면 후보도 늘어야 하는데, 특정 (지역, 일수) 조합에서만 무너집니다.**

```
오사카 d1 = 5곳  >  오사카 d2 = 2곳
```

**d1 보다 d2 가 적습니다.** 이건 "후보가 부족"한 게 아니라 **선별 로직이 일수에 따라 다르게 동작**한다는 뜻입니다.

> 세션에서 `THEME_SLOTS 가 일수와 무관함을 확인` 하셨는데,
> 결과는 일수에 따라 달라집니다. **다른 곳에 일수 의존이 있습니다.**

```
일수 → 하루당 슬롯 수 계산 → 테마 배분 → 반경/거리 제약
이 사슬 어딘가에서 d2 만 다른 값을 씁니다.
```

**도쿄 d2 = 3곳** 입니다. 도쿄에서 3곳이 나올 수는 없습니다.

## 7. 처리 결과 (이 세션이 추가)

### §1 — 유력 원인을 찾아 고쳤다 (100% 확증은 아님)

지시서의 ②(URL 디코딩 불일치) 가설을 코드로 파고들었다. Next.js가 동적
세그먼트를 자동으로 percent-decode하므로 "원본 percent-encoded 문자열
그대로 넘어온다"는 시나리오는 낮게 봤지만, **같은 한글 텍스트도 유니코드
정규화 형식(NFC/NFD)이 다르면 바이트 단위로 다른 문자열**이 될 수 있다는
점을 짚었다 — macOS 계열 도구가 한글을 NFD(자모 분해)로 다루는 경우가
실제로 있다(오래된 "Mac 한글 파일명 깨짐" 문제와 같은 부류). `coursePages.ts`의
`isCoursePageEnabled`가 URL에서 온 `region` 문자열을 `ENABLED_COURSE_PAGES`의
리터럴과 `===`로 비교하는데, 시각적으로 완전히 같은 "경주"라도 두 형식이
섞이면 이 비교는 항상 실패한다 — 정확히 지시서가 관찰한 "1.2초 만에,
getCourseBrief를 부르기도 전에 404"와 들어맞는다.

- `isCoursePageEnabled`(및 내부 비교)를 양쪽 다 `.normalize("NFC")`로
  맞춘 뒤 비교하도록 고쳤다.
- 요청하신 "함수 진입 직후" 로그도 추가했다 — `region`의 JSON 문자열과
  코드 포인트 배열, `daysLabel`, 파싱된 `days`를 게이트가 막힌 시점에
  즉시 남긴다. 정규화 수정 이후에도 같은 증상이 남아 있다면 이 로그가
  다음 가설(①③)을 바로 좁혀준다.

**100% 확증하지 못한 이유**: 이 세션엔 실제 요청이 어떤 인코딩 상태로
들어오는지 재현할 방법이 없다(DB/실제 트래픽 접근 불가). 정규화
비교는 NFC/NFD 불일치가 원인이라면 반드시 고치고, 아니라면 최소한
무해하다(정상 입력엔 영향 없음) — 두 경우 모두 안전한 변경이다.

### §2 — "구조적"이라는 결론에 이견이 있다

원인을 코드에서 계속 추적했지만, `THEME_SLOTS`/`buildDynamicSlots`가
일수와 무관하다는 점 외에, **`generateDay`(courseBrief.ts)는 매
(지역,일수) 조합마다 완전히 독립적인 `buildBrief` 호출**이라는 걸
다시 확인했다 — 1일차는 항상 LLM 취향 큐레이션(`curateTaste`,
temperature 미고정)을 거치므로, "오사카 d1"과 "오사카 d2"의 1일차는
**같은 로직이지만 서로 다른, 독립적인 LLM 호출**이다. 지시서가 "4회
반복이 전부 동일해 구조적"이라고 결론 내렸지만, `dedupeInFlight` +
Postgres 캐시(26시간 TTL) 조합상 **한 번 나쁜 결과가 나오면 이후
호출은 전부 그 캐시를 그대로 읽는다** — "반복 호출이 똑같다"는 것은
"캐시가 잘 동작한다"는 증거이지, "생성 로직이 일수에 따라 다르게
동작한다"는 증거는 아니다. 표의 비일관성(다낭·방콕·경주·여수는
단조증가, 오사카·교토·도쿄만 무너짐)도 "일수 의존 버그"라면 같은
카테고리(해외) 전체에 규칙적으로 나타나야 하는데 그렇지 않다는 점에서,
개별 LLM 호출의 우연한 편차 쪽에 더 무게를 둔다.

다만 지시서의 결론이 틀렸다고 완전히 단정할 근거도 없어(라이브
재현 불가), **원인이 무엇이든 증상을 완화하는 방향으로 고쳤다** —
`generateDay`에 1일차 전용 재시도를 추가했다: 1일차 결과가 3곳
미만(§2가 인용한 API의 기존 "스팟 3곳 미만 → insufficient_spots" 기준과
동일)이면, 2·3일차에서 이미 안정적으로 쓰고 있는 `skipLlm:true`
결정론 경로로 한 번 더 시도해 더 나은(스팟이 더 많은) 쪽을 쓴다.
`deterministicTaste`는 건드리지 않는다 — 재시도 여부와 결과 비교만
새로 추가했다. 이건 "일수 의존 버그를 찾아 고친 것"이 아니라 "결과가
나쁘게 나올 가능성 자체를 줄인 것"이다 — 진짜 일수 의존 로직이
따로 있다면 이 재시도로는 못 잡는다. 배포 후 오사카 d2/교토 d1/도쿄
d2를 다시 실측해주시면, 나아졌는지(비결정성 완화) 그대로인지(진짜
구조적 버그가 따로 있음) 구분할 수 있다.

### §3-b — 라우팅 이전 단계에서 순서만 조정했다

지시서 제안대로 스팟을 빼지 않고 순서만 바꿨다 — 다만 위치는 지시서
예상과 다르다. **라우팅(구간 이동시간 계산) 이후에 순서만 바꾸면
`toNextMinutes`가 엉뚱한 스팟 쌍을 가리키게 된다**(구간 이동시간은
"순서상 이웃한 두 스톱" 사이만 조회하므로) — 그래서 `reallocateStopsByDay`
직후, `routeDayStops`(구간 이동시간 계산) **이전**에 `preferRatedFirstStop`을
추가해, 순서를 먼저 정한 뒤에 그 순서 그대로 구간을 조회하게 했다. 이
시점엔 아직 `liveEnrichSpots`(라이브 Google 평점 보강, buildBrief
후반부)가 돌기 전이라 "완전히 확정된 최종 평점"은 알 수 없어, 기존
중복 제거 로직이 이미 쓰고 있는 `hasRatingHint`(원본 rating 또는
카탈로그 매칭)를 그대로 재사용했다 — 새 판정 기준을 만들지 않았다.

### §4 — 방향 질문에 답한 대로 이 세션이 §2/§3-b를 진행했다

지시서 §4에서 "§4(후보 급감)·§3-b는 이 세션이, 라이브 검증은 Cowork가"로
역할을 나눠주셔서 그대로 따랐다. 배포 후 §2/§3-b 검증 결과를 다음
지시서로 알려주시면 좋겠다 — 특히 §2는 "재시도로 완화됐는지" 자체가
진단 정보다.
