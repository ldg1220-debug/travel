## 5. ★★ dedupeInFlight 로는 결정성이 안 잡힙니다

원인 재진단은 정확했습니다.

> `실제 비결정성의 근원이 Math.random 이 아니라 LLM 호출(seed 파라미터 없음)`

**`pickDeterministic` 이 이 경로에서 호출조차 안 된다는 확인, 좋습니다.** 제 지시서가 틀렸던 부분입니다.

다만 `dedupeInFlight` 는 **동시 요청만** 합칩니다.

```
오늘 12:xx   경주  12곳 · 19.8km
오늘 13:xx   경주   9곳 · 22.3km     ← 시간이 지나자 다른 결과
```

```
연속 2회 호출  →  9곳 동일 (캐시 적중)
캐시 만료 후   →  또 달라짐
```

**구글이 재방문할 때마다 내용이 바뀝니다.** 색인에 좋지 않습니다.

```
LLM 에 seed 가 없으면
  · temperature = 0 으로 고정
  · 그래도 흔들리면 LLM 큐레이션 결과 자체를 캐시에 영구 저장
    (COURSE_ALGO_VERSION 이 오를 때만 재생성)
```

**"생성은 한 번, 이후엔 읽기"** 가 되어야 합니다.
지금은 캐시가 만료될 때마다 새 코스가 나옵니다.

## 9. 처리 결과 (이 세션이 추가)

### §4 — 로컬에서는 원인을 확정하지 못했다

빌드 산출물을 다시 확인했다 — `next build` 출력에 `ƒ /course/[region]/[days]`가
그대로 있고, `.next/server/functions-config-manifest.json`에도
`"/course/[region]/[days]": {"maxDuration": 60}`이 정상적으로 기록돼
`page.tsx`가 빌드에 포함되지 않은 것은 아니다(②는 로컬 기준 배제).
`③`(`/course` 도구 페이지와의 충돌)도 파일 구조상 변화가 없어(round 1부터
동일) 이번 회귀의 새 원인으로 보기 어렵다.

**`④`(maxDuration)도 근거로 배제한다** — `/api/content/course-brief`(§3에서
실측으로 200이 확인된 라우트)도 정확히 같은 `export const maxDuration = 60`을
쓰고 있다. 같은 계정·같은 배포에서 같은 값이 다른 라우트에서는 동작하므로,
계정/플랫폼 차원에서 60초가 허용되지 않는다는 가설은 성립하지 않는다. 또한
이 페이지 자체도 라운드 1(PR #261, `a64229e`)에서 동일한 `maxDuration = 60`으로
배포됐을 때 라우트가 정상 인식됐었다(당시 문제는 §2의 캐시 divergence였지,
라우트 인식 자체는 아니었다) — 그래서 이번 라운드에서 값을 낮추거나 지우지
않았다.

**이 샌드박스는 Vercel 런타임 로그·빌드 로그에 접근할 수 없어, 정확히
무엇이 다른지 확정하지 못했다.** 대신 두 가지 방향으로 대응했다:

1. **방어적 안전장치**: `loadEnabledCourseBrief`의 catch를
   `UnsupportedRegionError`만이 아니라 **모든 에러**로 넓혔다 — 문서의
   증상(제목이 Next 자체 not-found 문구가 아니라 콜론 표기의 Vercel
   플랫폼 404에 더 가까움)이 "처리되지 않은 예외로 페이지가 죽었다"는
   가설과도 맞아떨어진다. `getCourseBrief`가 무엇을 던지든(외부 API
   일시 장애, 환경 변수 문제 등) 이제 로그만 남기고 제어된 notFound()로
   내려간다 — 원인 불명의 크래시보다 안전하다.
2. **명시적 런타임 선언**: `export const runtime = "nodejs";`를 추가했다
   — 이 페이지가 Postgres(`pg`, Edge 런타임 비호환)를 쓰는 `getCourseBrief`를
   부르므로, 런타임 추론에 어떤 애매함도 남기지 않기 위해서다. 비용 없는
   방어적 변경이다.

**중요한 관찰 하나를 덧붙인다**: §3의 "데이터는 정상입니다" 증거
(`course-brief?region=경주&days=2`)는 **days=2**를 쓴다 — 그런데 문제의
페이지는 `days=3`(2박3일)을 쓴다. 서로 다른 캐시 키(`briefCacheKey`가
scope:region:days:algoVersion로 만듦)라, 이 증거는 "days=2는 캐시가
warm하다"만 보여줄 뿐 **days=3의 라이브 생성(캐시 미스)이 실제로
성공하는지는 여전히 확인되지 않았다.** 만약 days=3 조합의 `buildBrief`가
프로덕션에서 실제로 에러를 던지고 있다면(환경변수·API 키·rate limit 등),
위 1번 안전장치가 크래시를 막아주긴 하지만 여전히 404를 준다 — 근본
해결은 아니다. Cowork가 `/api/content/course-brief?region=경주&days=3`
(캐시가 없는 지역이 있다면 그쪽으로)를 직접 호출해 확인해주면 이 갈래를
좁힐 수 있다.

### §5 — 동의: "생성은 한 번, 이후엔 읽기"가 맞는 방향이다

`temperature=0` 고정 또는 LLM 큐레이션 결과의 영구 캐시화는 코스 생성
품질/캐시 무효화 정책에 영향을 주는 결정이라, 라우트 인식 문제(§4, 최우선)를
먼저 해소하지 않은 채 손대면 두 문제가 뒤섞여 원인 추적이 더 어려워진다고
판단해 이번 라운드에는 넣지 않았다 — 문서 §7 우선순위와도 일치한다
(§4 먼저, §5는 그다음).

### sitemap — 계속 제외 상태로 둔다

`COURSE_PAGES_IN_SITEMAP`은 여전히 `false`다. 이번 라운드의 수정이
근본 원인을 확정적으로 고쳤다고 확신할 근거가 없어(로그 접근 불가), Cowork가
실제 200을 확인하기 전까지 켜지 않는다.
