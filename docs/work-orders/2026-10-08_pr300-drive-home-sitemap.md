## 처리 결과

### §2 — 완료 (홈에 Drive)
- 홈(`/`) 서버 페이지에 `TravelpayoutsDriveScript`를 넣었다. 코스 상세(`/course/{지역}/{일수}`)에도 넣었다 — 지시서가 "`/course/**` 유지"라고 했지만 #246 이후 코드는 `/course`(목록)에만 있었고 상세 페이지엔 없었다. 이제 `/`·`/discover`·`/course`·`/course/**` 네 곳이다.
- 제외 유지: `/planner/**`(조건부 클라이언트 로드, 공유 토큰 있는 뷰), `/trip/**`, 공유 토큰이 URL에 있는 모든 페이지. 가드 테스트로 `planner/[shareToken]`·`trip/[id]` 서버 컴포넌트가 정적 Drive를 넣지 않는지 확인한다.
- 스니펫은 `emrldtp.com/NTYzMDg1.js?t=563085` 그대로다(`travelpayoutsDrive.ts`의 기존 IIFE — 사용자가 보낸 스니펫과 src가 같다). 홈 HTML에 src가 정확히 한 번 들어가는지 테스트한다.
- **주의**: `/planner`가 조건부 로드라는 점은 그대로다 — 계획 화면에서 제휴 링크가 보일 때만 클라이언트가 주입한다. 홈 로드는 `/planner`로의 SPA 이동 뒤에도 문서에 남아 있다면(Next 클라이언트 내비게이션은 `<head>`에 붙은 스크립트를 제거하지 않는다) 계획 화면에서도 이미 로드된 상태일 수 있다 — 그 경우 `location=`에 계획 토큰이 실릴 수 있다는 #246의 우려가 부분적으로 되살아날 수 있다. 라이브로 확인하지 못했다.

### §3 — 완료 (사이트맵을 빨리 채운다)
- ① **버전 무관 기록**: `course-sitemap:{지역}:{일수}` 키(`place_candidate_cache`, 버전 없음)에 "이 조합이 API 기준(`isCacheableBrief`)과 페이지 기준(얇은 콘텐츠)을 통과한 시각"을 남긴다. 브리프 생성이 끝나 캐시에 쓸 때마다 갱신한다. 사이트맵은 (현재 버전 캐시에서 판정한 목록) ∪ (최근 30일 기록)이며 같은 조합은 최근 시각을 쓴다 — 캐시 버전이 올라가도 사이트맵에서 빠지지 않는다. 기존 30일 정리(`courseRecommend.ts`)가 곧 "최근 30일" 기준이다. 기록은 사이트맵 읽기 시점에 한 번 더 일수 범위(1~7)를 확인한다.
- ② **시간 예산 워밍**: 12건 고정 대신 후보를 최대 60건 뽑고, 시작 마감(55초)까지 동시 3개로 새 조합을 계속 시작한다(캐시 히트는 0.2초·미스는 10~21초 — #300 실측). 마감 뒤에는 새로 시작하지 않아 진행 중인 것만 끝난다(최대 ~21초 → `maxDuration` 90초 안). 응답에 `processed`·`skippedByDeadline`·`elapsedMs`를 싣는다.
- **지시서와 다르게 한 것**: "90초 예산 안에서 실측 후 최대치로"의 실측은 이 세션에서 못 한다 — #300 실측 지연값으로 마감을 정했고, 배포 후 첫 실행의 `elapsedMs`·`processed`로 조정해야 한다. 캐시 히트 건너뛰기는 별도 코드 없이 `pickStaleTasks`의 정렬(캐시 없는 것 먼저)과 위 시간 예산으로 달성한다.
- ③ **우선순위 풀**: 해외 popularity 상위 40개 지역 × (도시형 2·3일 · 휴양형 3·5일)을 먼저 — 기존 `ENABLED_COURSE_PAGES`와 합쳐 중복 제거. 우선 풀 몫은 회당 24건까지(이전 8). 나머지는 지역 × 일수 전체 일반 풀. **국내는 popularity 값이 없어**(해외만 채워진다) 우선 풀에서 기존 24곳(`ENABLED_COURSE_PAGES`)만 먼저 돈다.
- **한계**: Hobby 플랜 하루 1회 크론이라 한 번에 최대 약 20~30건의 캐시 미스를 채울 수 있다고 추정한다(실측 전). 사이트맵은 몇 주에 걸쳐 자란다. 페이지 방문(크롤러 포함)도 캐시와 기록을 채운다.
