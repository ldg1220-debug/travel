## 1. ★★★ 지금 구글에 404 20개를 제출하고 있습니다

```
sitemap.xml   총 30 URL  (기존 7 + 코스 20 + 후기 3)

/course/경주/2박3일    →  HTTP 404
/course/강릉/2박3일    →  HTTP 404
/course/여수/2박3일    →  HTTP 404
/course/전주/2박3일    →  HTTP 404
```

**sitemap에 등록된 코스 URL 중 확인한 4개가 전부 404입니다.**
색인은 고사하고, 404를 대량 제출하면 사이트 신뢰도가 깎입니다. **가장 급합니다.**

## 2. ★★★ 단서 — 메타데이터는 성공하고 본문만 실패합니다

브라우저로 `/course/경주/2박3일`를 열었을 때입니다.

```
<title>   "경주 2박3일 코스 — 12곳, 총 19.8km"     ← 정상 생성됨
<body>    "404 | This page could not be found."    ← 본문은 404
```

**`generateMetadata`는 course-brief를 성공적으로 불러옵니다.**
12곳·19.8km라는 실제 값을 알고 있습니다.

```
즉  데이터는 있습니다.  page 컴포넌트가 notFound() 를 던지고 있습니다.
```

### 어디를 보면 됩니다

```
① 얇은 콘텐츠 게이트 (스팟<5, 평점없음≥50%)
     → 12곳이니 "스팟<5"는 아닙니다
     → "평점 없는 곳 50% 이상" 판정이 과한지 확인하세요
② 국내 상위 20개 화이트리스트 매칭
     → sitemap 생성기와 page 가 같은 목록/같은 비교 방식을 쓰는지
     → 한글 URL 디코딩 시점이 서로 다른지 (encodeURIComponent 비교 주의)
③ days 파싱
     → "2박3일" "3" "2박 3일" "2n3d" 모두 404였습니다
```

**sitemap 생성기는 20개를 통과시켰는데 page 는 전부 막습니다.**
두 곳이 같은 판정 함수를 쓰지 않고 있다는 뜻입니다. **하나로 합치세요.**

### 테스트가 이걸 못 잡은 이유

```
vitest 407개 통과  ·  next build 통과
```

**단위 테스트는 게이트 함수를 직접 부르고, 실제 라우트를 부르지 않습니다.**
`/course/{지역}/{일수}` 가 200을 주는지 확인하는 테스트를 추가하세요.

## 3. ★★★ 큰 검색어를 버리고 있습니다 — 서울·부산·제주·인천

`/api/content/regions` 는 이렇게 생겼습니다.

```
domestic: [ {name:"종로", parent:"서울"}, {name:"해운대", parent:"부산"}, … ]  61개
parent 값:  서울 · 경기 · 인천 · 강원 · 충청 · 전라 · 경상 · 부산 · 제주   9개
```

`name` 만 쓰면 **부모 9개가 빠집니다.** 그런데 실측해보니 이렇습니다.

```
course-brief?region=서울&days=2   →  200 · 12곳 · 영등포전통시장, 이랜드크루즈 …
course-brief?region=부산&days=2   →  200 · 12곳 · 자갈치시장, 초량밀면, 부전시장 …
course-brief?region=제주&days=2   →  200 · 10곳 · 서귀포매일올레시장, 용머리해안 …
course-brief?region=인천&days=2   →  200 · 12곳 · 신포국제시장, 코스모40 …
```

**전부 정상 응답하고, 실제 그 지역 장소입니다.** 발리 같은 오매칭도 없습니다.

```
"서울 여행 코스"  ·  "부산 2박3일"  ·  "제주 여행 코스"
```

**검색량이 가장 큰 키워드들입니다.** 지금 20개 목록(경주·강릉·속초·여수·순천·통영·거제·전주…)에
이 넷이 없습니다.

```
1단계 목록에 서울·부산·제주·인천을 넣으세요.
```

> AutoPipeline 세션이 "서울·부산·제주·인천이 공식 목록에 없다"고 판단했는데,
> **`name` 만 본 결과입니다. `parent` 도 course-brief 가 받습니다.**
> 그쪽에도 같은 내용을 지시서로 보냈습니다.

## 8. 처리 결과 (이 세션이 추가)

이 세션(2026-09-22 대응)이 위 §2~§5를 처리하며 확인·결정한 내용을 남긴다 —
다음 라운드가 "왜 이렇게 했는지" 다시 조사하지 않도록.

### §2 원인 — 실측으로 100% 확증하지는 못했다

이 샌드박스엔 DB/외부 API 접근이 없어 프로덕션과 동일한 조건으로 재현하지
못했다. 대신 코드 추적으로 다음을 확인했다:

- `getCourseBrief`가 캐시 미스일 때 부르는 `buildBrief`(→`generateCourseV2`)의
  후보 선정엔 진짜 무작위성이 있다(`courseRecommend.ts`의
  `pool[Math.floor(Math.random()*pool.length)]`).
- `isCourseBriefThin`(얇은 콘텐츠 게이트)은 캐시가 반환한 스팟 배열에 대해
  매번 새로 계산된다 — 캐시에 저장되는 값이 아니다.
- generateMetadata와 페이지 본문이 React `cache()`로 같은 함수를 공유해도,
  Next.js 16의 스트리밍 메타데이터("Next.js can render and send the initial
  UI to the browser, without waiting for `generateMetadata` to complete")는
  둘을 사실상 별도 실행 트랙으로 다루는 것으로 보인다 — 정확한 내부
  메커니즘은 이 세션에서 끝까지 확증하지 못했다.

세 사실을 합치면: 캐시가 비어 있을 때 두 호출이 각자 독립적으로
`buildBrief`를 한 번씩 더 돌리면, 완전히 같은 region·days를 넣고도 무작위성
때문에 서로 다른 스팟 조합이 나올 수 있다 — 하나는 얇은 콘텐츠 게이트를
통과하고 하나는 통과하지 못해 정확히 문서 §2가 관찰한 증상(메타데이터 성공,
본문만 notFound())이 나온다.

**메커니즘을 완전히 증명하진 못했지만, 고친 방식은 메커니즘과 무관하게
안전하다** — `/course/{지역}/{일수}` 공개 페이지는 이제 `getCachedCourseBrief`
(캐시 미스 시 라이브 생성으로 폴백하지 않고 곧장 null)만 부른다. 요청
경로에서 라이브 생성을 아예 없앴으니, generateMetadata와 페이지가 몇 번을
따로 부르든 항상 같은(결정적인) 결과를 받는다. 라이브 생성은 이제
warm-course-brief 크론(하루 1회, 이미 존재)에서만 일어난다 — 크론이 아직
안 돈 지역·일수는 크론이 돌 때까지 그대로 404고, 다음 실행 뒤엔 저절로
채워진다.

지시서 §2가 제시한 세 가지 후보(① 게이트 과함 ② 화이트리스트 불일치
③ days 파싱) 중, 코드 확인 결과 sitemap 생성기와 page는 처음부터 같은
`@/lib/coursePages` 모듈(`isCoursePageEnabled`)을 썼다 — "두 곳이 같은
판정 함수를 쓰지 않는다"는 지시서의 진단은 문자 그대로는 맞지 않았다.

### §3 — 서울·부산·제주·인천은 days=2(1박2일)로만 켰다

지시서가 실측한 건 `days=2`뿐이다. 기존 20곳(days=3, 2박3일)과 같은
일수인지 이 세션에서 검증할 방법이 없어(DB/API 접근 불가), 검증되지 않은
조합을 새로 켜지 않았다 — `ENABLED_COURSE_PAGE_REGIONS`(지역 배열)를
`ENABLED_COURSE_PAGES`((지역, 일수) 쌍의 명시적 목록)로 바꿔, 지역마다
다른 일수를 허용할 수 있게 구조를 바꿨다.

### §5 — noindex를 선택했다 (404 대신)

`/trip/[id]`는 이미 `TripPostClient.tsx`(클라이언트 컴포넌트)가 세션을
다시 확인해 비공개 글의 내용을 가린다 — 그 클라이언트 로직을 건드리지
않고, `generateMetadata`의 폴백 메타데이터(글이 없거나 비공개일 때)에만
`robots: { index: false, follow: false }`를 추가했다. 지시서가 "404를
주거나 noindex를 넣으세요"로 둘 다 허용했고, noindex 쪽이 기존 렌더링
경로를 바꾸지 않아 회귀 위험이 훨씬 낮다.
