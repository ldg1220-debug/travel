## 1. ★★★ 일자별 동선 지도 — `course-map?day=N`

블로그 7일 글에 **7일 전체 지도 한 장이 일자마다 반복**됩니다(`course-maps/…/7/v14.png`).
동근님 판단: *"같은 이미지 쓸 거면 하나만 하든지, 일자별로 동선 이미지를 따로 따든지."*

**일자별이 맞습니다.** 이미 재료가 있습니다 — #256 에서 OG 이미지용 **"대표 하루만 그리기"** 를 만들었습니다.

```
GET /api/content/course-map?region=세부&days=7&day=3
  → 3일차 스팟 · 구간 경로만 그린 지도
  → 캐시 키에 day 포함 (…/7/d3/v14.png)
  → day 가 범위 밖이면 400
```

```
· 번호 마커는 그날 순서대로 1부터
· 줌은 그날 스팟에 맞춤 (하루 동선이 한 동네면 크게)
· 기존 전체 지도(day 없음)는 그대로
· course-brief 응답에 dayImageUrls: [url1, …] 를 같이 주면 AutoPipeline 이 바로 씁니다
```

## 처리 결과

### §1 — 완료 (일자별 동선 지도)

- `GET /api/content/course-map?region&days&day=N` — `day`가 있으면 그
  하루 지도로 302 리다이렉트, 없으면 기존 전체 지도 그대로. `day`가
  정수 1..days가 아니면 400(코스 생성 전에 걸러냄).
- 일자별 지도는 **course-brief 생성 시 함께 만들어** `brief.dayImageUrls`
  ( `(string | null)[]`, i번째 = (i+1)일차)에 담는다 — course-map은 그
  캐시에서 꺼내 리다이렉트만 하므로 전체 지도와 같은 캐시를 타고
  요청마다 새로 그리지 않는다. 그 날짜 지도를 못 만들었으면(키 미설정·
  생성 실패) 그 자리는 `null`, course-map은 404. 구조 캐시 단계(지도
  생성 이전)에는 빈 배열 — `imageUrl: null`과 같은 의미.
- Blob 경로: 전체 지도 경로의 버전 세그먼트 앞에 `d{N}` 삽입
  (`course-maps/overseas/세부/7/d3/v15.png`) — 지시서 §1의 "캐시 키에
  day 포함" 그대로, 버전이 마지막 세그먼트라 알고리즘 버전이 오르면
  자동으로 새 경로가 된다.
- 지도 내용: 그날 스팟·그날 구간 경로만, 번호 마커는 그날 순서대로
  1부터(`buildStaticMapUrl`의 새 `numbered` 옵션 — 1~9번은 숫자 라벨,
  Static Maps 라벨이 단일 문자라 10번부터는 라벨 없는 small 마커),
  줌은 그날 스팟의 핵심 군집(`excludeOutlierSpots` → `computeViewport`,
  #256 OG 지도와 같은 함수)에 맞춤. 전체 지도·OG 지도는 기존 그대로.
- 전체 지도와 일자별 지도는 병렬로 생성한다(각각 독립 5초 타임아웃) —
  직렬이면 일수만큼 늘어날 지연을 한 번으로 묶는다. **Google Static
  Maps 호출이 코스 생성 1회당 1건 → 1+days건으로 늘었다**(지도 API는
  Places보다 훨씬 싸지만 비용 항목이 늘어난 건 사실이다).
- `dayImageUrls`가 없는 옛 캐시는 `isFreshBriefPayload`가 미스로 취급.

### §2 — 완료 (앵커 전용 후보 검색) · **지시서와 진단이 다르다**

**#279가 경주에서 효과가 없던 실제 원인은 "후보 풀에 불국사가 없다"가
아니라 내 코드의 결함이었다(코드로 확인).** #279의
`pickLandmarkAnchors`는 슬롯 후보 풀(`fetchSlotCandidates`)에서
`rating != null`인 후보만 앵커로 뽑는데, 국내(경주·서울·부산)의 슬롯
후보는 Kakao Local 결과라 **평점·리뷰 수가 아예 없다**(`kakaoToPlace`).
국내에서는 후보가 전부 걸러져 앵커가 한 곳도 안 만들어졌다 — 그래서
경주가 v14 재생성 후에도 그대로였다. 서울·부산의 개선은 #279 때문이
아니라(같은 이유로 앵커가 없었을 것이다) 다른 요인으로 보인다 —
라이브로 확인하지는 못했다. 지시서의 "반경 밖" 가설은 검증하지 못했고,
이 결함 하나만으로도 관찰된 현상이 설명되므로 근거 없는 반경 조정은
하지 않았다(다만 아래처럼 반경 필터는 지시서대로 새로 넣었다).

지시서가 요구한 "앵커 전용 후보 검색"이 이 결함의 정확한 해법이라
그대로 구현했다:

- `courseRecommend.ts` `fetchLandmarkCandidates(scope, city)` — **국내·
  해외 모두 Google Places**(리뷰 수를 주는 유일한 출처)로 검색한다.
  검색어 `"{도시} 관광명소"` + `includedType=tourist_attraction`, 최대
  20건, 슬롯 검색과 같은 품질 하한(attraction)·여행사/교통시설 제외
  적용. 결과는 `place_candidate_cache`(`landmark:` 키, 슬롯 캐시와 안
  겹침, 7일 TTL)에 저장해 **Places 호출을 지역당 7일에 1건으로
  묶는다**(새 비용이 생기는 지점이라 캐시를 뒀다).
- `pickLandmarkAnchors` — 평점 없는 후보 제외(§3), **코스 스팟 중심
  반경 20km 밖 제외**(지시서 "15~20km"), 리뷰 수 내림차순 **상위 5**
  중에서 이미 코스에 있는 곳을 뺀 앞의 **3곳**(지시서 "상위 5 → 앵커
  3곳"). `placeLandmarkAnchors`(서로 다른 날 분산·식사 슬롯 보호·교체
  방식)와 `courseRecommendV2`의 거리 점수는 그대로 — 지시서 판단대로
  공유 로직은 건드리지 않았다.
- **한계**: Text Search에는 좌표 반경을 걸 수 없어(도시 중심 좌표를
  이 모듈이 모른다) "검색 반경 확대"는 하지 못했다 — 대신 위 20km
  필터를 후보 선별 단계에 뒀다. 실제로 "경주 관광명소" 상위 20건에
  불국사·석굴암·대릉원이 들어오는지는 이 세션이 라이브로 확인하지
  못했다.

### §3 — 이번 라운드에서 다루지 않음 (로그 대기 중)

지시서 스스로 "로그가 오면 이어서 지시서를 드립니다"라고 했고, 이
세션은 Vercel 로그에 접근할 수 없어 `raw/valid/gated` 로그의 실제
출력을 볼 수 없다. 오사카 d2의 422 원인은 로그 확인 후 다룬다.

### `COURSE_ALGO_VERSION` — 완료 (14→15)

앵커 후보 검색·일자별 지도가 전부 최종 브리프 조립 로직에만 있어
원본 후보 캐시와 무관하게 이 버전에만 반영된다.

### 검증 관련 메모

이 세션은 프로덕션 Vercel 로그·GCP 콘솔·라이브 API 호출에 접근할 수
없어, §5 표의 실측(세부 `day=3` 2곳·번호 1·2, `dayImageUrls` 7개, 경주
d3에 불국사·대릉원, 서울·부산 회귀 없음)은 코드 검토·단위 테스트·
라우트 테스트로만 검증했다. 일자별 지도가 실제로 Google Static Maps에서
번호 마커와 함께 그려지는지, 경주 앵커가 실제로 잡히는지는 Cowork가
배포 후 §5 표 그대로 확인해야 한다.
