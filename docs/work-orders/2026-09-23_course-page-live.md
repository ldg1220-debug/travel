## 8. 처리 결과 (이 세션이 추가)

### §3 — d1 1번 스팟, 완료 (원인 정정)

지시서의 원인 추정("라우팅이 이동거리 기준으로 재배치")은 실제 코드와는
달랐다 — `routeDayStops`(planRouteForDay)는 거리 기준 재정렬을 하지
않는다(도달 불가능한 구간만 순서 그대로 걸러낸다). 실제 원인은:
`preferRatedFirstStop`은 라우팅 **이전**, 카탈로그 매칭까지만 평점
신호로 본다. 국내 스코프에서 카탈로그에 없는 스팟은 그보다 한참 뒤인
`liveEnrichSpots`(Google Places 라이브 조회)를 거쳐야 비로소 평점이
생긴다 — 경주 d1의 경주중앙시장·경주원조콩국·테라로사 경주점·
경주보문관광단지 넷 다 카탈로그 미매칭이었고, 테라로사(★4.5)·
보문관광단지(★4.3)는 라이브 조회로만 평점이 채워졌다. 그래서
`preferRatedFirstStop` 시점엔 "이 날엔 평점 있는 곳이 없다"로 보여
순서를 못 바꿨다.

지시서가 제안한 두 번째 방향("라우팅 결과를 받은 뒤 1번만 교체하고 그
두 구간의 이동시간만 재계산")을 그대로 구현했다: `liveEnrichSpots`
이후 최종 평점이 확정된 시점에 `findRatedFirstStopSwapIndex`(순수
판단 함수, 단위 테스트 있음)로 하루씩 다시 확인해, 1번 자리와 상대
위치의 "내용"(이름·카테고리·평점·좌표)만 맞바꾸고 order/day(자리)는
그대로 둔다. 좌표가 바뀌는 구간(최대 3개 — (0,1)·(j-1,j)·(j,j+1))만
실제 경로를 다시 조회해 이동시간·거리·지도 경로(mapPath)를 갱신하고,
나머지 구간은 다시 조회하지 않는다. 새 구간 중 하나라도 "no-route"면
그 날은 통째로 되돌린다(원래 1번 유지) — 보수적 원칙.

### §4 — 고베·오사카·교토 d2, 완화 재시도로 완료 (부분 해결 가능성 있음)

`courseRecommendV2.ts`(공유 스코어링 함수, 라이브 검증 없이 손대지
않기로 한 기존 결정 유지)를 직접 조사한 결과: `avoidCentroid`/
`avoidCuisines`는 후보를 제거하지 않는 연성 점수 페널티였고(제거 원인이
아님), 실제 후보 수를 줄이는 하드 필터는 `excludeIds`(정확히 같은
장소)와 `excludeNames`(`sameShop` 기준 — 같은 브랜드면 지점이 달라도
전부 제외)뿐이었다. 또한 `generateCourseV2` 내부엔 이미 반경 자동
확장(escalation, 15→30→60→120분) 장치가 있어 반경 자체를 넓히는
건 의미가 없었다.

고베처럼 원래 후보 풀이 작은 지역은 하루가 쓴 몇 곳의 "브랜드"까지
`excludeNames`로 통째로 빠지면 다음 날짜 후보가 급격히 줄 수 있다는
가설을 세우고, 기존 1일차 재시도 패턴(`MIN_DAY0_STOPS` 미만이면 재시도
후 `pickBetterDayResult`로 더 나은 쪽 선택)을 2일차 이후에도 동일하게
적용했다: 날짜별 최종 결과(`dedupeCrossDay` 이후)가 3곳 미만이면
`excludeNames`만 뺀(`excludeIds`는 유지 — 완전히 같은 장소 반복은 계속
막음) 재시도를 한 번 더 하고, 둘 중 스팟이 더 많은 쪽을 쓴다.

**단, 이 세션엔 라이브 API/DB 접근이 없어 고베·오사카·교토가 실제로
이 완화로 살아나는지는 직접 확인하지 못했다.** 만약 이 지역들의
근본 원인이 "후보 데이터 자체가 원천적으로 부족"이라면(예: 고베의
관광지 좌표 데이터가 discoverData.ts/실시간 검색 양쪽에서 다 얇은
경우) 이 재시도로도 3곳을 못 채울 수 있다 — 그런 경우는 이번 수정
범위를 넘는 별도 데이터 보강 작업이 필요하다. Cowork가 배포 후
§7 체크리스트로 직접 확인해야 한다.

### §5 — 조사 처리, 완료

`src/lib/coursePages.ts`에 `pickJosa`/`hasFinalConsonant` 헬퍼를
추가했다. 유니코드 한글 음절 코드(U+AC00~U+D7A3, (초성×21+중성)×28+
종성 구조)를 이용해 마지막 글자의 종성(받침) 유무를 판정하고,
`buildCourseIntro`의 "을(를)" 하드코딩을 `pickJosa(top.name, "을", "를")`
로 교체했다 — "황리단길을 포함해", "향미사를 포함해"처럼 받침 유무에
맞게 나온다. 한글 음절이 아닌 문자로 끝나는 경우(드묾)는 받침 없는
쪽을 기본값으로 둔다.

### §2 — 워밍 크론, 완료 (우선순위 분리 + 주기 단축)

`pickStaleTasks`가 전체 태스크(수백 개) 풀에서 가장 오래된
`BATCH_SIZE`(12)개만 뽑다 보니, sitemap에 올라가는 24개
(`ENABLED_COURSE_PAGES`)도 그 큰 풀 안에서 순번을 기다려야 했다 —
`src/app/api/cron/warm-course-brief/route.ts`에서 이 24개를 별도
풀(`PRIORITY_TASKS`)로 떼어 매 실행마다 고정된 몫(`PRIORITY_BATCH_SIZE`=8)을
먼저 배정하고, 남는 자리만 나머지 태스크에 준다 — 전체 `BATCH_SIZE`는
그대로라 실행 시간 예산(90초)에 새 위험을 더하지 않는다. 함께
`vercel.json`의 크론 주기를 하루 1회(`0 5 * * *`)에서 6시간마다
(`0 */6 * * *`)로 줄였다 — 24개를 8개씩 나눠도 3회(18시간) 안에
전부 한 바퀴 돌아 TTL(26시간)보다 여유 있게 갱신된다.

**Vercel 요금제에 따라 크론 실행 빈도에 제한이 있을 수 있다(예: 일부
플랜은 하루 1회로 강제 조정)** — 이 세션엔 Vercel 대시보드 접근 권한이
없어 실제 배포 후 6시간 주기로 정상 실행되는지 확인하지 못했다.
Cowork가 배포 후 Vercel Cron Jobs 화면에서 실행 이력을 확인해야 한다.

### §1 — 24개 워밍 후 sitemap 플립, 이번 라운드에서는 다루지 않음

대신할 수 없으므로 `COURSE_PAGES_IN_SITEMAP`은 플립하지 않았다.
