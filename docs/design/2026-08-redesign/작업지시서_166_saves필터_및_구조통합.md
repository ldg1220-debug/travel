관련: PR #166 / 커밋 `0b82cfe`

## 1부. 버그 — 원인 확정

### 증상 (사용자 스크린샷)

동일한 나고야, 동일한 라이브 데이터인데 화면마다 결과가 다릅니다.

| 화면 | 결과 |
|---|---|
| `/discover` → 해외 → 지역별 → 아시아 › 일본 › 나고야 | **"이 조건에 맞는 장소가 아직 없어요."** (빈 화면) |
| `/course` → 아시아 › 일본 › 나고야 → 관광지 | 나고야 성 `★4.2 · 44,988` / 시케거리 `★4.0 · 693` / 엔도지 상점가 / 나고야항 수족관 / 가토 기요마사 상 / 나고야 도검박물관 **정상 표시** |

### API는 정상

```
GET /api/discover/trends?scope=overseas&category=region&path=아시아,일본,나고야
→ notice: "live", trending: 24건
```

### 원인 — `saves: 0`

라이브 스팟과 큐레이션 스팟의 필드를 전량 대조한 결과, **차이가 `saves` 하나뿐**입니다.

| 필드 | 큐레이션 (오사카 `o-t1`) | 라이브 (나고야 `live:ChIJ…`) | 판정 |
|---|---|---|---|
| `saves` | 3120 | **0** (24건 전부) | ⚠️ **유일한 차이** |
| `tag` | 관광지 | 관광지 / 음식점 / 카페 | ✅ 동일 |
| `region` | 일본 · 오사카 | 일본 · 나고야 | ✅ 동일 형식 |
| `season` | summer | summer | ✅ 동일 |
| `iconKey`·`gradient`·`color`·`lat`·`lng` | 있음 | 있음 | ✅ 동일 |
| `rating`·`reviewCount` | 없음 | **있음** (4.2 / 44,988) | 라이브만 보유 |

필드 구조는 오히려 라이브 쪽이 더 풍부합니다. 누락 필드는 없습니다.

**`saves: 0`은 #163의 "가짜 숫자 금지" 원칙에 따라 의도적으로 넣은 값인데,
`/discover`의 랭킹·필터 로직이 `saves`를 기준으로 동작해 24건이 전부 탈락합니다.**

`/course`가 정상인 이유: `/course`는 `saves`를 쓰지 않고 `rating`/`reviewCount`로 정렬합니다
(스크린샷의 `★4.2 · 44,988` 표기, 그리고 관련도순/인기순/별점순/리뷰많은순 정렬 옵션).

보강 근거 — `0b82cfe` 디버그 블록 관측값:
```
trendingRealLen=24 → trendingCompactLen=4
```
24건이 압축 단계에서 걸러지는 필터가 실재함을 보여줍니다.

### 조치

`DiscoverClient.tsx` 및 `/api/discover/trends`에서 `saves`를 참조하는 지점을 전수 확인:

- `filter(s => s.saves)` / `saves > 0` / `saves >= N` 형태 → **원인일 가능성 높음**
- `sort((a,b) => b.saves - a.saves)` 후 상위 N 자르기 → 정렬 자체는 무해(전부 0이면 순서 유지)하나,
  이후 임계값 컷이 붙어 있으면 문제

**권장 수정: 라이브 스팟의 랭킹 키를 `saves` → `reviewCount`로 대체.**

- 라이브 스팟은 `reviewCount`를 실제로 보유(나고야 성 44,988)하며, 이게 곧 인기도 신호
- 가짜 숫자를 만들지 않으면서 랭킹이 의미를 가짐 (#163 원칙 유지)
- `/course`가 이미 쓰는 방식과 통일됨

대안(차선): `id.startsWith("live:")` 또는 `notice==="live"`일 때 `saves` 필터를 우회.
동작은 하지만 랭킹이 무순서가 되므로 위 안을 권합니다.

### 완료 조건

- `/discover` → 해외 → 지역별 → 아시아 › 일본 › 나고야 에서 카드 24건 표시
- `/course`의 나고야 목록과 상위 스팟이 대체로 일치
- 라이브 안내 배너("실시간 검색 결과로 보충해드려요") 정상 노출
- 국내 미큐레이션 시/군에서도 동일 확인
- 회귀: 큐레이션 도시(오사카·다낭)의 기존 정렬이 바뀌지 않을 것

## 2부. 구조 고찰 — `/discover`와 `/course`를 나눠 둘 이유가 있는가

### 결론 요약

**지금 형태로는 나눠 둘 이유가 약합니다. 다만 완전 통합이 아니라
"공통 탐색 표면 1개 + 상위 의도 레이어 2개"로 재구성하는 것을 권합니다.**

이번 버그가 그 근거입니다 — 같은 데이터·같은 카드인데 한쪽만 깨졌고,
그 사실을 발견하는 데 여러 라운드가 걸렸습니다.

### 현재 중복 현황 (직접 관측)

| 요소 | `/discover` | `/course` | 중복 |
|---|---|---|---|
| 국내/해외 토글 | 있음 | 있음 | ✅ |
| 지역 드릴다운 | 지역별 칩 → 대륙›국가›도시 | 국내/해외 → 시도 → 시군구 | ✅ (구현 별개) |
| 스팟 카드 + 담기 | 있음 | 있음 (`+ 코스에 담기`) | ✅ |
| AI 동선 배너 | 있음 (보라 그라데이션) | 있음 (동일 디자인) | ✅ |
| 라이브 검색 | #166에서 신규 배선 | 이미 있었음 | ✅ (두 번 구현) |
| 지표 표기 | `saves` (이번 버그) | `★rating · reviewCount` | ❌ **불일치** |
| 정렬 옵션 | 없음 | 관련도/내주변/인기/별점/리뷰/가격 | ❌ |

마지막 두 줄이 핵심입니다. **`/course`는 이미 지표 문제를 해결해 뒀는데
`/discover`만 `saves`에 묶여 있어 이번 버그가 났습니다.** 통합돼 있었다면 발생하지 않았습니다.

### 실질적 차이 (유지할 가치가 있는 것)

| 축 | `/discover` | `/course` |
|---|---|---|
| 사용자 의도 | **어디 갈까** (목적지 미정) | **정한 곳에서 뭐 할까** (목적지 확정) |
| 카테고리 성격 | 콘텐츠 분류 (관광지·자연·음식점) | **일정 슬롯** (점심 맛집·저녁 맛집·숙소) |
| 고유 표면 | 계절별·최근 핫한·추천 코스 템플릿·후기 | 테마·이동 반경·세부 설정(시작/종료/이동수단) |

`점심 맛집`/`저녁 맛집`/`숙소`는 탐색용 분류가 아니라 **하루 일정의 슬롯**입니다.
이 구분은 의미가 있어서, 단순 병합하면 오히려 흐려집니다.

### 권장안 — 공통 표면 추출

```
        [공통] 장소 탐색 표면
        · 지역 드릴다운 (하나의 트리)
        · 스팟 카드 + 담기
        · 지표 표기 (rating · reviewCount 통일)
        · 라이브 검색 폴백 (한 곳에서만 구현)
                    ▲                  ▲
         ┌──────────┘                  └──────────┐
   /discover (영감 레이어)              /course (조립 레이어)
   · 계절별 · 최근 핫한                 · 테마 · 이동 반경
   · 추천 코스 템플릿 · 후기            · 세부 설정(시작/종료/이동수단)
   · "어디 갈까"                        · 슬롯 기반 카테고리
```

**얻는 것**

- 이번 같은 "한쪽만 깨짐" 부류가 구조적으로 사라짐
- 라이브 검색·placeholder 필터·지표 표기를 한 번만 구현
- `/discover`에도 정렬 옵션과 평점 표기가 자동으로 생김 (현재 없음)
- 지역 트리 구현이 하나로 (현재 국내는 canonical 스켈레톤, 해외는 spot 파생 — 이원화)

**감수할 것**

- 리팩터 범위가 작지 않음 (두 클라이언트 컴포넌트 모두 손댐)
- 지금 #166이 열려 있어 충돌 가능 → **#166 병합 후 별도 PR 권장**

### 함께 볼 문제 — 홈 진입점 중복

이 대화 초반에 지적했던 것과 같은 뿌리입니다. 홈 카드가:

- **여행 계획짜기** → `/discover`
- **계획** → `/planner`
- (discover 안의 배너) → `/course`

세 개가 전부 "계획"이고, 이름만으로 구분이 안 됩니다.
공통 표면을 추출하면 진입점도 자연스럽게 정리됩니다 — 예:

- **어디 갈까 정하기** → 영감 레이어
- **일정 짜기** → 조립 레이어 + 플래너

1. **지금**: 1부 `saves` 버그 수정 → #166 병합
2. **다음**: 공통 표면 추출 리팩터 (별도 PR)
3. **그다음**: 홈 진입점 네이밍 정리

2번은 신규 기능이 아니라 정리 작업이라 눈에 보이는 성과가 없지만,
앞으로 discover/course 양쪽을 건드리는 작업마다 비용이 두 배로 드는 걸 막습니다.
지금이 적기인 이유는 #164·#166으로 두 화면의 데이터 소스가 방금 같아졌기 때문입니다.

## 부록 — 이전 보고 정정

지난 턴에 보고한 **"scope desync"(배너는 나고야인데 카드는 국내 데이터)는 오관측이었습니다.**
사용자 스크린샷을 보면 scope·breadcrumb·칩이 모두 정상이고 카드만 비어 있습니다.
제 JS 클릭이 스코프 전환을 구동하지 못한 상태에서 관측한 것이 원인입니다
(프로덕션 대조에서 동일 실패 확인 → 검증 방법 문제로 판명).

**교훈: 이 세션의 브라우저는 SPA 상호작용을 구동하지 못합니다.
UI 검증은 사용자 스크린샷으로, 자동 검증은 API 레벨로 분리하는 것이 정확합니다.**
이번에도 스크린샷 2장이 API 검증만으로는 못 잡을 지점을 정확히 짚었습니다.
